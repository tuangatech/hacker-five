## Why this doc exists

An LLM agent that drives HackerFive — reasoning about which targets/templates to run, sequencing scans through the CLI, and triaging findings — is a sound design, and it's consistent with how the field already builds this category of tool. This doc has three parts: (1) why HackerFive's *existing* architecture already leans toward the "hacker-in-the-loop" model without having been built with an agent in mind, (2) what other LLM-driven pentesting tools' designs teach about doing this well — updated to what those projects actually became, not just their launch announcements, and (3) the concrete changes HackerFive needs to make agent integration actually safe — the main content of this doc, now including the specific mechanisms (not just the open questions) for the harder design points.

## 1. How HackerFive already aligns with "hacker-in-the-loop"

"Hacker-in-the-loop" is the term the bug-bounty industry has converged on: an AI agent may reason, execute, and reconnoiter autonomously, but a human must validate findings before they reach a program, and a human must approve any consequential action. HackerOne restated this directly in its February 2026 "Responsible AI" update: hackbots must not operate fully autonomously, the default configuration requires a human-in-the-loop to verify before anything with real consequences happens (a submission, a payout), and every agent action and its reasoning must be traceable with a full audit trail. Its separate Hai platform documentation adds the operational detail: agentic features follow that same default, and for autonomous features specifically, the customer defines the authorized scope, targets, and operational guardrails *before* the agent begins — not after.

HackerFive was not designed with an agent in mind, but several decisions already made in doc02/doc13 put it ahead of a typical "staple an LLM onto raw CLI tools" approach — because the guardrails already live in the *tool*, not just in whatever a prompt tells the model to do:

| Existing design decision | Where it's specified | How it already embodies hacker-in-the-loop |
|---|---|---|
| `Finding` struct + `Exporter` interface | doc02 §5 | Structured, machine-readable output an agent can reason over directly — no parsing free-form tool text |
| `--scope` "warn, don't silently proceed" | doc02 §3 / `Engine.Run` | The guardrail is enforced by the tool itself, not by trusting an agent's judgment |
| Host-error-cache circuit breaker | doc02 §3 | Bounds how hard an agent can hammer a broken/unreachable target, regardless of what it decides to do |
| `--allow-writes` opt-in gate | doc13 Step 3 | Already framed as the one sanctioned, explicit, human-consented exception to read-only — exactly the shape a "consequential action" gate needs |
| Self-hosted, user-provided OOB server | doc13 Objective §1 | No target data leaves the operator's own infrastructure no matter what an agent probes |
| Pinned-commit template sync | doc10 / doc12 | An agent can't be steered by a compromised upstream template landing between pins |
| HackerOne `Exporter` = "report-drafting, not unattended submission" | doc13 Step 4 | This *is* the platform's human-in-the-loop submission rule, already built in before any agent exists |
| Credentials via environment variable only | CLAUDE.md | An agent's own context/prompt can't leak a secret that was never hardcoded to begin with |
| Baseline two-account IDOR comparison / fixed-path misconfig matching | doc02 §3 | A concrete, reproducible technical condition already gates every `Finding` — the same "don't trust a bare model opinion" property every serious 2026 pentesting agent had to add on top of an LLM (see Section 2's "PoC required" thread) |

Two structural properties matter more than any single line item:

- **Template metadata is agent-legible.** Every template's `info:` block already carries `name`/`severity`/`tags`/`description` — natural-language metadata an LLM can match against its own recon observations ("this response shape looks like GraphQL — pull graphql-tagged templates") in a fuzzier and more capable way than Nuclei's own static tag matching.
- **The web UI's engine hooks double as agent infrastructure.** Doc12 specs `WithFindingCallback`/`WithLogCallback` on `scanner.Engine` — Phase 3 (Week 19) has since actually built and shipped them for the web UI's SSE handlers, so this is no longer a proposal, it's real code (`pkg/scanner/engine.go`) an agent orchestrator can reuse directly, live events to reason over mid-scan rather than a JSON blob only after everything finishes.
- **The deterministic matcher/extractor engine is already HackerFive's "PoC required" guarantee.** Every detector doc02 specs — IDOR's baseline two-account comparison, misconfig's fixed-path-plus-keyword match, auth-bypass's multi-step state comparison — already requires a concrete, reproducible technical condition before something becomes a `Finding`. This is the exact property that every credible 2026 agentic pentesting tool had to build or bolt on to avoid an LLM's bare opinion counting as a result (Section 2, "PoC required" thread). Decision 2 in Section 3 makes it explicit that agent integration must not quietly open a second, opinion-only path to a `Finding` that bypasses this.

The gap, covered in Section 3, is that none of this was designed to be *called* by something other than a human at a terminal, and none of the human-approval boundaries above are currently enforced against an automated caller specifically. Section 3 also now resolves the questions the original draft of this doc left open — orchestrator shape, tool surface, and the approval mechanism — with citations to how the field actually settled them.

## 2. How LLM-driven pentesting tools structure themselves (updated for 2026)

The original version of this table summarized launch-week claims. A year-plus later, several of these projects have shipped enough real usage, benchmark data, and (in one case) a public embarrassment to say something more concrete than "here's the design." Ordered roughly by how directly reusable the lesson is for HackerFive:

| Tool | Structure / design | Human checkpoint / safety mechanism | Key lesson for HackerFive |
|---|---|---|---|
| **Cyber-AutoAgent** — open-source, reached 84.62% (88/104) on the XBOW benchmark, the first open-source project to hit XBOW's own baseline | Rebuilt from a multi-agent design into a single "meta-agent": one decision-maker that spawns short-lived swarm agents as tools, writes new tools for itself at runtime (`load_tool`), and self-assesses confidence in bands (High >80%, Medium 50-80%, Low <50%) before committing to a path | None built in by design — explicitly experimental, lab-only, and the maintainer archived the repository in 2026 citing the time investment needed to reach production maturity | A real, measured data point, not a design opinion: the project's own writeup reports zero coordination failures, zero resource conflicts, and zero task-handoff errors after moving *away* from a multi-agent architecture. This is the strongest evidence available against defaulting HackerFive's agent to a peer-agent mesh (see Decision 1, Section 3) |
| **MAPTA** — academic, open-science reproduction of the XBOW benchmark methodology | Three fixed roles: a Coordinator (strategy/orchestration), one or more Sandbox agents (tactical execution in an isolated per-job container), and a Validation agent (mandatory PoC execution) | Findings require validated PoC evidence, not a model's assertion | Published full cost accounting across 104 challenges ($21.38 total, median $0.117/challenge) and found tool-call count, dollar cost, token count, and wall-clock time are all *negatively correlated* with success (r = −0.66, −0.61, −0.59, −0.56 respectively). That's a concrete, evidence-based basis for an early-stopping/prioritization rule — not just a severity score (see Section 3, Group H) |
| **XBOW** — commercial, first AI system to reach #1 on HackerOne's US leaderboard, now integrated into Microsoft Security Copilot | A coordinator provides ongoing orchestration and a decision engine, debriefing short-lived, mission-scoped "attack worker" agents that are retired after each mission specifically to avoid bias; a separate validator confirms reproducibility | Every scan's scope is customer-defined before agents begin; every action is logged and auditable; the CISO explicitly frames the human's role as reviewing whether each action stayed within the bounds of "part of the penetration test" | Confirms the coordinator-plus-disposable-workers shape at production scale, not just in a lab benchmark — this is the same shape MAPTA and Cyber-AutoAgent converged on independently |
| **Strix** — open-source (Apache-2.0), the highest-profile 2026 entrant (32.8k★, #1 GitHub Trending day it broke out); ~96% (100/104) on the XBEN benchmark at roughly $3.37/challenge | Coordinator arranges specialized agents (recon, exploit via HTTP-proxy/browser/Python sandbox, validation) into a graph; a finding is not reported without a working proof-of-concept | `--max-budget-usd` is a first-class, documented hard cap on LLM spend for a run; `--scan-mode quick\|deep` and `--diff-scope`/`--non-interactive` with non-zero exit codes are built specifically for CI gating; the project's own docs are explicit that "zero false positives" is a design goal, not a guarantee — a human still triages severity and blast radius | The PoC-required rule is the practical hallucination filter (an agent can imagine a bug, it can't fake a working exploit for one that doesn't exist); a first-class spend ceiling and CI-friendly exit codes are table stakes for anything meant to run unattended, not optional extras |
| **CAI (Cybersecurity AI)** — open-source framework, Alias Robotics | "Eight pillars" — Agents, Tools, Handoffs, Patterns, Turns, Human-In-The-Loop, Extensions, Tracing — running a ReAct (Reason+Act) loop, with a dedicated `CostTracker` for budget enforcement and multi-layer input/processing/execution guardrails (toggleable via `CAI_GUARDRAILS`) | HITL is a first-class pillar, not a wrapper: the docs state a "man-in-the-loop" principle explicitly — operators can pause, inspect, or take direct control of a running agent at any point | Treating guardrails and cost tracking as core architectural pillars (not bolted on) is the cleanest available reference for how to structure HackerFive's own budget/approval layer. **Caveat:** CAI's own GitHub repository carries an archival notice as of this writing, with development moving to a commercial successor ("CSI"); the architectural pattern is still worth reusing independent of that project's current maintenance status |
| **HexStrike AI** — open-source MCP server, 150+ wrapped security binaries, 12+ "AI agents" | One decision engine picks tools/parameters from a large catalog exposed via MCP; the project's *own documentation* teaches users to open a session by asserting ownership of the target so the underlying model's built-in reluctance is talked past, rather than the tool enforcing anything itself | None in the base project. A community fork ("Hexstrike 7 PL") had to add a Security Validation Layer — command validation, rate limiting, API authentication, a tool whitelist, and parameter sanitization — after the fact | The clearest evidence available, in public, that bolting guardrails on after release is worse than starting with them. This is the anti-pattern doc90's first draft warned about, now with a specific example of someone having to fix it |
| **PentestGPT** — the original USENIX 2024 paper's design, now split into two live modes | `pentestgpt-legacy` preserves the original tripartite architecture: Reasoning, Generation, and Parsing modules cooperating over a **Pentesting Task Tree (PTT)** — an attack-tree-derived structure the Reasoning module updates. A verification step on every PTT update checks that *only leaf nodes* changed, which is the project's specific defense against a hallucinated rewrite of the overall plan. The 2026 rebuild adds a fully autonomous staged pipeline (recon → exploit → report) driven through Claude Code or Codex as the execution backend | Legacy mode requires the human to drive each step (`next`, `more`, `todo`, `discuss`); the autonomous pipeline persists a full session log. The project reports an 86.5% (90/104) result on a December 2025 XBOW validation-suite run, explicitly labeled a historical research result, not a standing guarantee | The leaf-only-mutation-plus-verification rule is a concrete, reusable mechanism for stopping an agent from silently rewriting its own plan to claim progress it didn't make — directly portable to a HackerFive task tree (Section 3, Group H) |
| **PentestAgent (GH05TCREW build)** — open-source, MCP-native | A running agent can call `spawn_mcp_agent` to spawn a child copy of itself as a subordinate MCP server over stdio; the child's full tool set is injected back into the parent after spawning — hierarchical delegation with no external orchestrator | Interactive REPL mode is the default; multi-agent/"crew" mode is opt-in | A workable pattern for delegation *if* HackerFive ever needs it, but Decision 1 (Section 3) argues against making this the default shape — noted here so a future contributor understands the alternative was considered, not missed |
| **Google Big Sleep** (Project Zero + DeepMind) — code-level, not black-box web | Iterative hypothesis → test-case → debug loop with sandboxed tool access, mirroring how a human researcher explores a codebase | Human-reviewed disclosure to the affected project before any public writeup | *Carried over from the original draft, not re-verified in this revision* — Big Sleep wasn't part of this pass's fresh research, so treat this row as the same information doc90 already had, not an update |
| **HackerOne's own platform policy** (Feb 2026 "Responsible AI" update; Hai Security & Trust docs, May 2026) | Formal, restated platform-wide policy: agents may reason and act multi-step, but the default configuration requires human-in-the-loop verification before any consequential action; the newer Agentic PTaaS product runs full recon-exploit-report cycles with a human validating findings before they reach engineering teams | Human-in-the-loop mandatory for every finding validated and for any consequential decision; full, traceable audit log of agent reasoning and actions; scope/guardrails must be defined by the customer *before* an autonomous agent starts | This is the current, restated version of the rule the original draft summarized from a year-old blog post. Worth re-citing directly: the language has sharpened, not softened, since the first draft of this doc |
| **The Thacker/xssdoctor "Singularity" hackbot** — individual bounty hunters, built on Claude Code skills | Recon and deep-analysis skills each hunter had already built individually, merged into one system; a "boss" role kicks off targets and tells workers to keep going or pivot; a second pass tries to kill weak/hallucinated claims before anything is reported | A human watches and redirects live via a full session stream (originally piped into Discord), including **live log injection** — typing directly into a running worker's log mid-task to nudge it without stopping it | Found 126 bugs over five months, including a blind NoSQL (`$where`) injection a human likely would have walked past. The team's own framing of the turning point: the difference between a useful hacking agent and an expensive hallucination machine was observability — not model quality, not tool count |

**Common threads across every serious 2026 implementation, updated:**

1. **A structured intermediate representation, not raw chat.** A task tree, a `Finding` schema, an exploit-flow graph — every design that works past trivial cases replaces "just keep talking to the model" with something structured the model reads and writes into. PentestGPT's leaf-only-mutation rule is the most concrete version of this available.
2. **Observability is a first-class feature, not a debugging afterthought.** The tools that treat session/reasoning logging as core infrastructure produce agents people actually trust; the ones that don't produce hallucination machines with good demos. The Thacker/xssdoctor build's live-log-injection feature goes one step further: observability that lets a human steer a running agent, not just watch it.
3. **A human checkpoint sits between the agent and anything irreversible.** Submission, payout, or a production write — every credible implementation puts a person at that specific boundary, no exceptions. HackerOne's Feb 2026 policy reconfirms this is the platform's actual enforced rule, not just good practice.
4. **Target/template prioritization is its own problem, solved partly outside the LLM.** MAPTA's measured negative correlation between resource spend and success is now a real, cited basis for this, not a hand-wave.
5. **The safety boundary belongs in the tool, not the prompt.** HexStrike's own documentation instructing users to talk the model into compliance, contrasted with the community fork that had to retrofit a validation layer, is about as clear as this evidence gets.
6. **New: a single coordinator beats a peer-agent mesh by default.** Cyber-AutoAgent's own ablation (multi-agent → single meta-agent, with a *measured* improvement) and XBOW/MAPTA's independent convergence on the same coordinator-plus-disposable-workers shape make this a real recommendation, not a stylistic preference.
7. **New: a hard, first-class spend/attempt ceiling is now standard practice, not a nice-to-have.** Strix ships `--max-budget-usd` as a top-level flag; CAI has a dedicated `CostTracker` pillar; MAPTA's cost-correlation finding gives a reason beyond "don't overspend" — it's also a signal that the agent is stuck.
8. **New: "PoC required" is the field's actual hallucination filter.** Strix and MAPTA both gate a reported finding on a working, reproducible exploit rather than a model's assertion. HackerFive already has the mechanism for this (deterministic matchers) — Decision 2 below is about not accidentally building a second path around it.

## Real design decisions resolved by this research

The original draft of this doc left several structural questions open. Following the same discipline Phase 4's own doc13 used for its three design tensions — resolved explicitly, with a stated reason, rather than left for whoever implements the step to guess — here are the four this research settles:

**1. Orchestrator shape: single coordinator vs. multi-agent mesh.**
`follow-up.md`-style question doc90 v1 posed as "should we have an operator or orchestrator." **Decision: one coordinating process, full stop — no peer-agent mesh by default.** Cyber-AutoAgent's own measured result (multi-agent → single meta-agent was a net improvement, not a wash) and XBOW/MAPTA's independent convergence on coordinator-plus-disposable-workers make this the evidence-backed default, not a stylistic call. Concretely: HackerFive's coordinator owns the task tree (Group H below) and calls into `pkg/scanner`/`pkg/template`/`pkg/reporter` the same way `pkg/webui` does today; any "spawn a sub-agent to dig into this one endpoint" is a scoped, disposable *tool call the coordinator makes to itself*, not a peer agent with independent judgment it has to reconcile against. This also sidesteps most of OWASP's Insecure Inter-Agent Communication risk (ASI07, Group D below) for free — there's only one agent whose "communication" matters.

**2. Tool surface: narrow, CLI-shaped MCP tools vs. a general shell/exec toolbox.**
HexStrike, CAI, and PentestAgent all give the model a general-purpose shell/terminal tool it can use freely. **Correction (found while researching [91-research-recon-phase.md](91-research-recon-phase.md)): this undercounts the field.** Strix's own docs list a bare "Terminal (Bash shell)" alongside its sandboxed Nuclei/ffuf; CAI's actual recon-category tool is `LinuxCmd` — general command execution; MAPTA's Sandbox agents get exactly two tools, `run_command` (shell) and `run_python`; and Cyber-AutoAgent "automatically chooses" nmap/sqlmap/nikto through a tool-selection API that's functionally the same pattern. Giving the model raw command execution is closer to universal than this sentence originally implied — full sources in doc91 §1. **Decision unchanged, evidence base strengthened: HackerFive's MCP server never exposes anything shaped like "run arbitrary command."** The tools are `scan`, `templates.list`, `templates.sync`, `findings.export`, and the new `plan` tool (Group B below) — each one schema-validated the same way `scanner.Config` already is, mapping 1:1 to an existing CLI verb. This isn't a limitation to relax later; it's the thing that keeps HackerFive's "PoC required" property (Section 1, Section 2 thread 8) intact. Every path to a `Finding` still runs through the existing deterministic matcher/extractor engine — the agent selects targets and templates and interprets results, it never gets to craft a raw request the engine's matchers didn't already validate. This is the direct, permanent answer to the temptation that will come up in a future phase ("just let the agent run curl/nmap directly for this one edge case") — the answer is no, add a template or a detector instead, the same way every non-agent feature request in this project already has to.

**Research note, 2026-09-02 (Strix tech-stack specifics, gathered comparing Go vs. Python as implementation choices — logged as reference, not a decision input):** Strix's own dependencies, confirmed via direct research rather than assumed: **LiteLLM** (multi-provider LLM abstraction), **Playwright** (browser automation — Python bindings are Playwright's first-tier target), **Caido** (HTTP interception), and — the load-bearing one for this section's topic — a **Docker-sandboxed Python runtime as a "Custom Exploit Runtime"**: the agent writes and executes real Python code to build/validate PoC exploits. Strix also reuses **Nuclei** (Go, the same engine HackerFive is modeled on) for its own template-driven detection — so even Strix doesn't do everything in Python; it's Python-orchestrated with a Go tool underneath for the deterministic part, the same split HackerFive already has, just with the orchestrator language swapped.

**Future reconsideration, not decided — logged 2026-09-02, prompted by the research note above.** The idea: a sandboxed-interpreter tool (Go or Python, shelled out from HackerFive regardless of which) specifically scoped to building/validating a PoC exploit, mirroring Strix's Custom Exploit Runtime. **This would require actually reopening Decision 2** — not a narrower carve-out beside it — since "write and run code that constructs/sends a payload against the target" is exactly the "run arbitrary command" shape this paragraph's "not a limitation to relax later" language currently forbids, and the same "permanent" framing is repeated in [14-implementation-plan-ph5.md](14-implementation-plan-ph5.md) Step 1, [15-implementation-plan-ph6.md](15-implementation-plan-ph6.md)'s "Explicitly out of scope," and [91-research-recon-phase.md](91-research-recon-phase.md) §5. Logging the idea here rather than silently dropping it, but **not acting on it**: reversing a decision cross-referenced this heavily needs its own deliberate discussion when it's actually reconsidered, not a quiet edit prompted by a comparative-research pass. If this is ever taken up, update all four cross-references above together, not just this paragraph.

**3. Human-approval mechanism: bespoke `--plan-only`/plan-ID flag vs. native MCP primitives.**
Doc90 v1's B1 proposed `hackerfive scan --plan-only` and a hand-rolled `--approve-writes <plan-id>` flag. **Decision: build this on MCP's native `elicitation` and `tasks` primitives (2026-07-28 spec) instead.** A server can now pause mid-call and ask the human a specific, in-context question before proceeding (`elicitation`), and long-running work has real, standard states — `working`, `input_required`, `completed`, `failed`, `cancelled` (`tasks`) — rather than a status string HackerFive would have had to invent and keep in sync with a client. This is a case where waiting turned out to be correct: the protocol grew the exact mechanism doc90 v1 was speccing from scratch, and it comes with whatever client-side approval UI the person's MCP host (Claude Desktop, Claude Code, etc.) already renders, instead of HackerFive needing to build one.

**4. Confidence vs. severity: one field or two.**
Not an open question doc90 v1 named explicitly, but a real trap this research surfaced: several tools' "confidence" and "severity" concepts blur together. **Decision: keep them as two separate fields on the data model.** `Finding.Severity` stays exactly what doc02 §5 / doc13 already spec it as — deterministic, CVSS-shaped, and never agent-writable. A new `Finding.Confidence` (and the task-tree-leaf-level success-probability it derives from, Group H) is the field the agent *does* get to set, following Cyber-AutoAgent's High(>80%)/Medium(50-80%)/Low(<50%) banding as a concrete starting convention. Conflating "how bad is this if real" with "how sure are we it's real" is a modeling mistake several of the tools above make implicitly; HackerFive doesn't have to repeat it.

**5. LLM invocation model: stateless, per-decision-point, tiered by model class — never a persistent agent driving execution.**
Not a question v1 or Decisions 1-4 addressed — those fix the orchestrator's *shape* (single coordinator) and *interface* (MCP tools, elicitation, confidence field) but leave open how an LLM actually gets invoked once real reasoning is needed. **Decision: the coordinator stays deterministic Go code — the same `Job.PlanTree` walker Decision 1 already describes — and at defined decision points it makes a single, stateless, schema-in/schema-out call to one of two model tiers. There is no persistent chat/agent session held open across a scan; every "LLM agent" call is a plain function from the orchestrator's point of view.** Two tiers, chosen by the decision's cost/frequency, not fixed per detector:
- **Local, small model** — cheap, frequent, low-stakes calls: routine judgment (does this fingerprint match look like a false positive, is this response shape worth a closer look), running entirely on the operator's own machine.
- **Frontier model via OpenRouter** — rare, expensive, high-stakes calls, principally authoring a new template when Decision 6's deterministic layer and the existing template corpus both come up empty.

Each call: build a prompt from the current `PlanTree` leaf's context, get back a schema-validated decision, apply it as a leaf mutation, continue — no conversation history carried between calls. This is the deliberate opposite of PentestGPT's persistent-reasoning-loop shape (Section 2), and it's the same "per-job state refreshed each run" philosophy Decision 4/H3 and doc91's Mem0-memory rejection already established, applied one level down to the invocation model itself. It also has a data-handling benefit beyond cost: only the rare frontier-tier call sends anything to a third party — most scan traffic never leaves the local-model tier or the deterministic layer at all, the same default-conservative posture [discussions.md](discussions.md) documents for `--oob-server` (a third party only in play when the user's own choice, default or explicit, calls for it).

**6. Tag/tool/template matching: deterministic decision-engine first, LLM only as a documented fallback.**
doc91's own recon-research draft framed "match `ReconResult` against template tags" as something "the coordinator" does — read literally, an LLM reasoning step, and a real ambiguity this decision resolves. **Decision: that matching is a static, versioned decision-engine registry (Go data, not a model call) — the same shape HexStrike AI's own `TechnologyDetector`/`IntelligentDecisionEngine` classes use internally (confirmed by reading its source directly, not just its docs): a tech-signature table maps a `TechFact` to a product name, and a tool-effectiveness/attack-pattern table maps that product to the detectors/recon-tools/template tags relevant to it.** The LLM (Decision 5) is invoked only when this registry has no entry for what recon actually found — an explicit "decision engine came up empty" trigger, never a parallel path the LLM can take just because it judges the deterministic answer insufficient. This keeps the expensive, harder-to-audit tier rare by construction, and gives HackerFive a shipped version of an idea the field has so far only proposed: Strix's own maintainers have an open, unimplemented GitHub issue (#46) proposing exactly this kind of deterministic fingerprint→plan scoring ("Target Complexity Index"), confirmed still unshipped as of this research. Group I below schedules the registry itself.

## What HackerFive needs to change — the concrete backlog

Grouped by concern, same convention as before. ⬜ = not yet designed in detail; treat this as a backlog to scope properly when it's actually scheduled, same discipline doc09-13 already apply to their own steps. Items carried over from the v1 draft keep their original letter/number; genuinely new items get a `(new)` tag the first time they appear so it's clear what this revision actually added versus what was already there.

**Suggested sequencing, not just grouping** — updated:
1. **The six Decisions above are prerequisites, not backlog items** — they constrain how A1, B1, Group H, and Group I get built, so read them before starting any of Section 3's numbered work, not concurrently with it.
2. **G1 (a crude eval-harness stub) still first, even before A1/B1.** Unchanged reasoning from v1: without it, every claim this effort makes about agent quality is unfalsifiable from day one.
3. **A3 (freeze the `Finding` schema) still before A1 (the MCP server) ships**, not concurrently — now with the added note that `Finding.Confidence` (Decision 4) must be part of that frozen schema from the start, not bolted on after an external client already depends on the shape without it.
4. **B1 (approval gate) before the rest of Section B** — now built on MCP `elicitation`/`tasks` per Decision 3, which also means B1 is smaller to build than v1 assumed, not larger.
5. **H5 (the per-job spend ceiling) is now sequenced alongside B1, not deferred to "later hardening."** A hard budget cap is one of the few items on this whole list with a same-day, out-of-the-box reference implementation to copy (Strix's `--max-budget-usd`), so there's no reason to treat it as a stretch goal.
6. **D2 (program-policy pre-flight check) remains a hard blocker for any agent-driven run against a real target.** Unchanged from v1 — still the one item with a documented real-world cost of skipping it (XBOW's own program removal).
7. **Group I (the decision engine) has no MCP dependency and sits ahead of Group H's confidence/prioritization work becoming agent-driven.** H3/H4 assume something is already picking which leaf to work on next; I3 is what populates real `PlanTree` leaves from a plain, non-agent `hackerfive scan`/`recon` run — build it whenever Phase 5's recon package (Group R) exists, not gated behind A1/B1.

### A. Structured, tool-callable interfaces
*Make HackerFive addressable by a machine caller, not only a human at a terminal.*

- ⬜ **A1 — MCP server (`pkg/mcpserver/`)** exposing `scan`, `templates.list`, `templates.sync`, `findings.export`, and `plan` (new, see B1) as MCP tools. Calls straight into the existing `pkg/scanner`/`pkg/template`/`pkg/reporter` packages — no scan logic duplicated, the same boundary doc12 already drew for `pkg/webui`. *(updated)* Built against the 2026-07-28 spec's `elicitation`/`tasks` primitives per Decision 3, and deliberately excludes anything shell/exec-shaped per Decision 2 — this is the one place in the whole backlog where "don't add a tool" is as important a design choice as "add a tool."
- ✅ **A2 — `Engine.WithFindingCallback` / `WithLogCallback` — already landed.** Unchanged from v1: doc12 specs these, Phase 3 (Week 19) actually built them for the web UI's SSE handlers (`pkg/scanner/engine.go`), so `pkg/mcpserver` (A1) just needs to consume the same hooks `pkg/webui` already does.
- ⬜ **A3 — Freeze and version the `Finding` JSON schema.** Publish it as `docs/schema/finding.schema.json`. *(updated)* Must include `Confidence` as a field distinct from `Severity` from the first published version (Decision 4) — this is exactly the kind of thing that's cheap to get right before an external MCP client depends on the wire shape and expensive to add later.
- ⬜ **A4 — `hackerfive templates list --json`.** Unchanged from v1: expose the same tag/severity/category data doc12/Week 19 already extract, as machine-readable JSON rather than a text table only.
- ⬜ **A5 — Tool-list scoping *(new)*.** Per OWASP's "least agency" principle (Group D below): an MCP session shouldn't necessarily see every tool in A1's list regardless of what it's doing. A read-only "triage this scan's findings" session and a "plan and (pending approval) run writes-capable business-logic checks" session are different levels of agency and should get different tool lists from the server, not the same list gated only by a runtime check inside each tool.

### B. Explicit human-approval gates
*Turn today's implicit caution into enforced checkpoints an automated caller cannot skip.*

- ⬜ **B1 — `plan` MCP tool, built on native `elicitation`/`tasks` *(re-scoped per Decision 3)*.** The agent proposes a full run (targets, detectors, templates, whether writes are required) and gets back a structured plan snapshot (the task tree, Group H) in `input_required` state — no request sent. The human's approval is an `elicitation` response, captured natively by the transport rather than a plan-ID string HackerFive has to mint, store, and trust the agent not to replay. Still the single highest-leverage change in this whole list: today the CLI just executes, and there is currently no point where a human sees and approves a plan before traffic goes out.
- ⬜ **B2 — Turn `AllowWrites` into an attested approval, not a bare boolean.** Unchanged from v1 in spirit: accepts only an approval tied to a plan a human already reviewed via B1 — now naturally an `elicitation` grant rather than a hand-rolled plan-ID check, so "no process, including an agent, can set the flag for itself in the same breath it decided it wanted to" holds by construction, not by convention.
- ⬜ **B3 — Document HackerOne submission as a permanent architectural invariant**, not a Phase-4-scoped decision. Unchanged from v1. Worth noting the reputational stakes are now demonstrated, not hypothetical: HackerOne's CEO had to publicly clarify in February 2026, after a researcher backlash, exactly how agentic features do and don't touch researcher data — a live example of how fast trust erodes if an agentic feature's boundaries aren't crisp and stated up front. HackerFive should hold itself to the same bar preemptively.
- ⬜ **B4 — Scope-creep gate.** Unchanged from v1: fresh approval required if a scan's own recon surfaces hosts/paths outside the original `--targets`/`--scope`.

### C. Observability and auditability
*The "traceable reasoning" requirement — and the difference the field's own builders call out between a useful agent and a hallucination machine.*

- ⬜ **C1 — Agent session log.** Unchanged from v1's core requirement (a structured, append-only record of every tool call, its stated reasoning, and the raw result), *(updated)* now with a concrete UI target: a Web UI "Agent" tab that streams this live over the same SSE mechanism `pkg/webui` already has, rather than a log file reviewed after the fact. The Thacker/xssdoctor team's own framing is worth repeating here because it's the single most load-bearing lesson in Section 2: the difference between a useful hacking agent and an expensive hallucination machine was observability, not model quality or tool count.
- ⬜ **C2 — Extend the audit trail doc12 already specifies for the Web UI's authorization checkbox** to also capture agent-specific facts. Unchanged from v1.
- ⬜ **C3 — Evidence-linked claims.** Unchanged from v1: no agent-drafted report text without a citation to a specific `Finding.ID` and its evidence.
- ⬜ **C4 — Live log injection *(new)*.** The Thacker/xssdoctor build supports typing directly into a running worker's log to redirect it mid-task without stopping it. Worth scoping as a stretch goal on top of C1's SSE stream: a text box on the Agent tab that appends an operator note into the coordinator's next reasoning turn. Lower priority than C1-C3, but cheap to add once C1 exists and directly useful for exactly the "it got distracted, nudge it" scenario every practitioner interviewed in Section 2 described hitting.
- ⬜ **C5 — Plan-preview UI, read-only then actionable *(new)*.** A Web UI page rendering `Job.PlanTree` — each leaf's target, detector/template, rationale, and `Confidence` band — is the only real way a human reviews *what* the agent is asking to do before B1's `elicitation` is granted; a raw MCP tool-call log (C1) isn't a decision surface by itself. Ships read-only in Phase 5 (nothing populates a live tree yet), gains Approve/Reject/Edit controls, a budget gauge against H5's spend ceiling, and an always-reachable kill switch in Phase 6, once there's a real `plan`/`elicitation` flow to act on.
- ⬜ **C6 — Recon-results UI *(new)*.** A Web UI page browsing a `ReconResult` (hosts/endpoints/tech stack/`OutOfScope`, each fact with its source/confidence label) — useful standalone for a human operator, independent of any agent session. Ships in Phase 5 alongside C5, since both are pure reads over data structures that exist with zero MCP dependency.

### D. Safety extensions specific to agent-driven operation

- ⬜ **D1 — Per-detector concurrency ceilings.** Unchanged from v1.
- ⬜ **D2 — Program-policy pre-flight check.** Unchanged from v1 — still a hard blocker, not a nice-to-have.
- ⬜ **D3 — Hard-fail, not warn, on missing `--scope` for agent-initiated runs.** Unchanged from v1.
- ⬜ **D4 — OWASP Agentic Top 10 (ASI01-10) mapping *(new)*.** OWASP published a peer-reviewed Top 10 for agentic applications in December 2025 (ASI01 through ASI10, reviewed by 100+ security practitioners including reviewers from NIST, Microsoft, and AWS). Rather than re-deriving guardrails from first principles, walk HackerFive's design against this list point-by-point once and record the result — mitigated, or explicitly accepted as residual risk with a stated reason, matching this project's own "revise down with reasoning, don't pad" discipline:

  | ASI risk | HackerFive-specific mitigation |
  |---|---|
  | ASI01 Agent Goal Hijack | Target responses are untrusted *data*, never instructions — the agent reasons about scraped HTML/JSON, it doesn't execute anything found inside it. D3 (hard-fail on missing scope) is the other half of this |
  | ASI02 Tool Misuse & Exploitation | Already addressed by Decision 2 (no shell/exec tool) plus A1's schema-validated, CLI-verb-shaped tool set |
  | ASI03 Identity & Privilege Abuse | Short-lived, per-call credentials for any MCP tool call that needs `--auth-token`-equivalent material — never baked into the agent's long-lived context, which is a much larger leak surface than a CLI invocation |
  | ASI04 Agentic Supply Chain Vulnerabilities | Already covered: pinned-commit template sync (doc10/doc12) and E2's staging directory for agent-proposed templates |
  | ASI05 Unexpected Code Execution | Avoided by design — Decision 2 means there's no code-execution tool to misuse in the first place |
  | ASI06 Memory & Context Poisoning | The task tree (Group H) is the durable state, refreshed each run from the engine's own results — not an open-ended conversational memory a target's responses could poison across sessions |
  | ASI07 Insecure Inter-Agent Communication | Mostly moot by construction — Decision 1's single coordinator means there's no peer-agent channel to secure |
  | ASI08 Cascading Agent Failures | Host-error-cache circuit breaker (already built, doc02 §3) plus the new per-job spend/attempt ceiling (H5) |
  | ASI09 Human-Agent Trust Exploitation | Approvals happen through the Web UI's audited controls or an MCP `elicitation` dialog — **never** through the agent simply reporting back "the user approved this" in its own conversational output. This is the direct implementation detail behind B1/B2 |
  | ASI10 Rogue Agents | An explicit, always-reachable kill switch/pause (C1's Agent tab) plus D2's program-policy preflight as a hard blocker |

- ⬜ **E2 — Agent-proposed templates land in `templates/proposed/`**, never directly in a trusted path. Unchanged from v1.

### G. Validation for the agent layer itself

- ⬜ **G1 — An eval harness against the existing lab targets** (crAPI, DVWA, vAPI, Juice Shop) with known findings, tracking agent-driven false-positive/false-negative rate *separately* from the underlying detectors' own measured rate. Unchanged reasoning from v1 — still shouldn't ship last despite the alphabetical position. *(updated)* Worth explicitly modeling the harness on the reproducible-benchmark discipline MAPTA and Cyber-AutoAgent both published (a fixed challenge set, a binary pass/fail per challenge, full cost accounting per run) rather than inventing a scoring rubric from scratch — this is a case where copying a public methodology is strictly better than a bespoke one, since it makes HackerFive's own numbers comparable to a known reference point.

### H. Task tree, prioritization & orchestration architecture *(new group)*

*Where Decisions 1 and 4 above actually get implemented — this group didn't exist in v1 because v1 didn't yet have a concrete mechanism to propose.*

- ✅/⬜ **H1 — Single coordinator, not a peer-agent mesh.** This is Decision 1 restated as a backlog item: there's nothing to "build" beyond *not* building the alternative. Worth keeping as an explicit checklist line so a future contributor doesn't reach for a "specialized recon agent + specialized exploit agent" architecture without first re-reading why that's not the default here.
- ⬜ **H2 — `Job.PlanTree`.** Extend the existing `Job` struct (`pkg/webui/jobs.go`, or a new shared type if both the MCP server and the Web UI need it) with a PTT-shaped tree: each node is a candidate (target, detector/template) pairing with a status and a rationale string; each leaf additionally carries a `Confidence` value (Decision 4). Mutations are restricted to leaves — any update touching the tree's shape is rejected, mirroring PentestGPT's own defense against a hallucinated rewrite of the plan (Section 2). Streamed over the same SSE channel `Job.Findings`/`Job.Logs` already use — this is a field addition to code that exists today, not a new subsystem.
- ⬜ **H3 — `Finding.Confidence` + leaf-level confidence bands.** Decision 4, implemented: High (>80%), Medium (50-80%), Low (<50%), following Cyber-AutoAgent's convention as a starting point rather than inventing a new scale. Drives what the coordinator works on next; never drives `Finding.Severity`.
- ⬜ **H4 — Cost/attempt-aware prioritization.** A per-leaf attempt counter and running spend tracker, with MAPTA's own measured finding as the concrete rule: rising tool-call count, dollar cost, token count, and elapsed time on one leaf are each independently correlated with *falling* odds of success, so "still grinding after N attempts with no confidence increase" should read as a stop-and-escalate signal, not a reason to allocate more budget to the same leaf.
- ⬜ **H5 — Per-job spend ceiling.** A hard, enforced cap (a `--max-budget`-equivalent, directly modeled on Strix's own flag) — not a warning, not a log line. Sequenced alongside B1 per the sequencing note above, not deferred.

### I. Decision engine & tiered LLM fallback *(new group)*

*Where Decisions 5-6 above get implemented — the deterministic dispatch layer, the shared capability registry, and the tiered LLM call it falls back to.*

- ⬜ **I1 — Capability registry.** One static, versioned catalog covering every dispatchable capability HackerFive has: built-in detectors (idor/misconfig/authbypass/ssrf/businesslogic/promptinjection), recon tools (subfinder/tlsx/dnsx/naabu/httpx/katana/interactsh), and template categories (tags from the synced `nuclei-templates` corpus plus HackerFive-native ones) — each entry carrying `name`, `description`, `when_to_use`/`when_not_to_use`, `cost/risk` (read-only vs. write, request volume), `inputs_required`. This is the answer to "should every tool be its own MCP tool": no — one `tools.search`/`templates.search` MCP tool (Group A) backed by this registry, search-then-fetch rather than list-everything-into-context.
- ⬜ **I2 — `pkg/fingerprint`: tech-signature detection.** Header/body/favicon/port signature matching producing/enriching `ReconResult`'s `TechFact` entries — the HexStrike `TechnologyDetector` pattern, reimplemented as first-party deterministic Go, not pulled in as a dependency.
- ⬜ **I3 — Decision engine: `TechFact` → registry match.** Deterministic dispatch (Decision 6): given a `ReconResult`, look up each detected `TechFact` in I1's registry and produce the matched detectors/tags/templates as real `PlanTree` leaves — no LLM, no MCP dependency, works from a plain `hackerfive scan`/`hackerfive recon` invocation. This is what actually populates a *live* `PlanTree` outside of any agent session — a real upgrade on Phase 5's original "read-only, fixture-only" framing for that data structure.
- ⬜ **I4 — Tiered LLM fallback (Decision 5).** Invoked only when I3 comes up empty for a leaf. Local small model for routine judgment calls; a frontier model via OpenRouter for the rare "draft a new nuclei-compatible template" case — whose output is untrusted input, run through the *existing* untrusted-template rejection pipeline (the `code:`/`javascript:`/`headless:`/`file:` block rejection already built for Phase 1b) before ever landing in `templates/proposed/` (E2) for human review. Every call is one input→output pair tied to a single `PlanTree` leaf, logged the same way C1 logs any other tool call.
- ⬜ **I5 — Recorded reuse audit**, so a future detector-class decision doesn't re-derive this from scratch: HexStrike AI's signature/decision-table pattern (I1-I3's direct model, confirmed via source read — `TechnologyDetector`, `IntelligentDecisionEngine`, `hexstrike_server.py`); Cyber-AutoAgent's smaller `risky_technologies` hint dict (a reasonable first cut of I1 before it grows HexStrike-scale); Strix's per-technology skill-file *content* (mined for domain knowledge — Firebase/Auth0/Supabase endpoint lists — not its LLM-routing mechanism, which doesn't transfer to a deterministic engine) and its dependency/SCA-scanning skill (a well-specified design worth adapting as a new detector class later, extending misconfig's existing `.git`/lockfile-exposure checks rather than a new package).

## Definition of Done ("Hacker-in-the-Loop Ready")

- [ ] An agent can call `scan` / `templates list` / `templates sync` / `plan` via MCP, consuming structured JSON — no shelling out to parse raw CLI text, and no tool shaped like "run arbitrary command" exists anywhere in the server (Decision 2)
- [ ] A single coordinator process drives every MCP tool call; any delegated sub-work is a scoped, disposable tool call the coordinator makes to itself, not an independent peer agent (Decision 1)
- [ ] Live findings and logs stream to the agent mid-scan, not only as a final batch
- [ ] `Job.PlanTree` exists, mutates only at leaves, and every write is verified against a wholesale hallucinated restructuring of the plan
- [ ] `Finding.Confidence` (agent-set) and `Finding.Severity` (deterministic) are separate fields; no code path lets the agent set severity (Decision 4)
- [ ] A per-job spend/attempt ceiling is enforced, not just logged, and ties into the attempt-aware prioritization rule (H4/H5)
- [ ] No path exists for an agent to set `AllowWrites` or submit a HackerOne report without a separate, human-granted approval step, captured via MCP `elicitation`/`tasks` (Decision 3) or the Web UI's audited controls — never via the agent's own conversational assertion that approval happened (OWASP ASI09)
- [ ] Every agent tool call and its stated reasoning is captured in a persisted, reviewable session log, visible live in the Web UI's Agent tab
- [ ] A missing `--scope` hard-fails an agent-initiated run rather than warning and continuing
- [ ] An agent-driven run against a real (non-lab) target refuses to proceed when the target's disclosure policy disallows automated scanners (D2) — treated as a hard blocker, not a soft warning
- [ ] Agent-proposed templates land in a staging directory and require human promotion before they're trusted
- [ ] HackerFive's design has been checked against all ten OWASP Agentic Top 10 risks (D4), with each either mitigated or explicitly accepted as residual risk with a stated reason
- [ ] Agent-driven false-positive/false-negative rate is measured against the lab targets using a benchmark methodology modeled on MAPTA/Cyber-AutoAgent's own published discipline, tracked separately from detector-level rate
- [ ] A deterministic decision-engine registry (I1-I3) resolves `TechFact` → detector/tag/template matches with zero LLM calls, live-verified against a lab target's real fingerprint
- [ ] The LLM fallback (I4) is confirmed, live, to trigger only when the registry has no match for a leaf — never as a parallel, always-available path (Decision 6)
- [ ] Every LLM call is a single, stateless input→output pair tied to one `PlanTree` leaf, with no persistent chat/agent session held open across a scan (Decision 5)
