- **LT-172 (IMPLEMENTED + live-verified 2026-09-20/21, branch `fix/agent-orchestrator-lt168-171-172`) — the LLM adds latency, not judgement, for the cheap deterministic part of the tree.** vAPI turns 1-6 (five single-template leaves plus the `netservice` port check) and DVWA turns 1-8 (all single-template leaves) each finished their scan in 0.1-1.6s with 0 findings, each preceded by a 1-4 min `NextAction` round trip. DVWA's model walked leaves in literal numeric order (leaf-1 … leaf-8; rationales on turns 4-8: "Continue scanning the next pending high-confidence Apache CVE check…"). The one broad, high-yield leaf — generic `misconfig`, which produced *all* of DVWA's 13 and vAPI's 10 findings — was picked **9th** and **7th**. Tool diversity was zero on DVWA (9/9 `scan.leaf`; no `recon.refresh`/`registry.lookup`/`triage.rank`). **Fix:** a deterministic *fast lane* — dispatch pending leaves in a yield/cost priority order (capability leaves before single-template leaves, then confidence) with no LLM call, and call `NextAction` only at genuine decision points: fast lane drained, a finding that warrants follow-up, an `unresolved` leaf, thin recon. This is the "LLM only at the few genuine gaps" rule from [CLAUDE.md](../CLAUDE.md) and answers LT-165 item 2's open question ("skip `NextAction` when one viable leaf — needs eval data") with data: on vAPI+DVWA 14 of 17 dispatched turns were exactly this shape. Expected effect: vAPI 14 min → ~3, DVWA bounded by scan time not LLM latency. Pairs with LT-171 (what the model sees at the points where it *is* called). **Shipped:** `orchestrator.Config.FastLane` (CLI `--fast-lane`, default true; `--fast-lane=false` restores one-model-call-per-turn; the Web UI agent path sets it on). A leaf is fast-lane when it is pending with a detector and is either a raw template-ID leaf (`registry.LeafClass == "templates"`) or a parameter-free sweep (`misconfig`/`netservice`/`tls`); those run in `Priority` order (the decision engine's own `leafPriority`) with no `NextAction` call, each leaf at most once, recorded as `TurnRecord.Auto` turns and counted in the new `Result.FastLaneTurns` (they count toward neither `MaxIterations` nor the `MinIterations` floor — the floor stays about the model's own turns, or a drained fast lane would satisfy it instantly and re-open LT-162's early-stop). idor/authbypass/ssrf/sqli/businesslogic leaves, `unresolved` leaves, recon.refresh, triage and stop remain model decisions. A cancelled context is checked each fast-lane iteration. **Live, port-pinned scope (the LT-168 form), same model, one target at a time:** DVWA — before: 9 model turns, hit the 20-min cap, exit 0 with 4 fixture prefixes; after: **0 model turns, 11 fast-lane turns, $0, exit 0, all 11 leaves done, same 4 prefixes** (1001s, of which 16 min is the one broad `misconfig` scan — see LT-179). vAPI — before: 8 turns, exit 1 after two 4-min stalls, ~14 min; after: **0 model turns, 16 fast-lane turns, exit 0, 133s, 5/5 prefixes**. Juice Shop — 1 leaf, fast lane, 0 model turns, 2/5 (unchanged; the 3 misses are the stale-fixture / probe items already logged). **Consequence worth knowing:** on DVWA/vAPI/Juice every leaf is parameter-free, so `hackerfive agent` there is now fully deterministic and *no longer exercises the LLM at all* — these labs stopped being an agent-reasoning test; crAPI (endpoint-specific idor leaves) is the one that is. Tests: `TestIsFastLaneLeaf`, `TestNextFastLaneLeaf_HighestPriorityFirstThenTreeOrder_SkippingTried`, `TestHasActionableLeavesExcept_IgnoresTriedPendingLeaves`, `TestRun_FastLane_RunsParameterFreeLeafWithoutAskingTheModel` (0 `NextAction` calls), `TestRun_FastLaneOff_StillAsksTheModelForTheSameLeaf`, `TestRun_FastLane_CancelledContextEndsTheRunWithAnError`. **Not done:** the "a finding that warrants follow-up" decision point (a fast-lane finding never pauses the lane; the model sees it only when the lane drains) and a yield-ordered lane that puts the broad sweep ahead of single-template leaves regardless of `Priority`.
- **LT-171 (IMPLEMENTED + live-verified on crAPI 2026-09-21, branch `fix/agent-orchestrator-lt168-171-172`) — the orchestrator prompt is blind to the three things it would need to reason.** `buildOrchestratePrompt` (`pkg/llmfallback/orchestrate.go:170`) renders leaves as `id/target/detector/status/confidence/rationale`, tools, and history; a `scan.leaf` turn's result is only `"N finding(s), M log line(s)"`. So: (1) **no finding detail** — the model never learns a finding's ID/severity/target/whether it's new, so it can't chain (`.env` exposed → try the leaked creds; 401 on an API → `authbypass`; `/metrics` → infra recon) and `triage.rank` has nothing to be chosen *for*. **Live proof of the damage — crAPI turns 3-4:** both dispatches returned `"1 finding(s)"`; the finding was the identical `nuclei-openresty-detect-0` info hit re-firing (LT-166), not an IDOR result — yet turn 4's rationale states "leaf-24 and leaf-23 already confirmed IDOR on the /workshop/api/mechanic API", a false belief built from a bare count. (2) **No recon facts** — tech+versions, endpoint list, open ports, `AppSurface`/WAF/uniform-wall verdict never reach the model, so `recon.refresh` is blind and any `script.explore` script has nothing concrete to ground on (the design premise of that tool — JWT alg-confusion, ID-space decoding — needs the endpoint/token facts). (3) **Leaf detail is buried** — an `idor` leaf's `EndpointTemplate` is only visible if the rationale string happens to embed it. **Fix:** three compact, capped, read-only digest blocks in the prompt (findings digest with a per-turn "N new / M duplicate", recon digest, leaf key fields). Touches no invariant: the model still can't write a `Finding`/`Severity`/`Confidence` (doc02 Design Principle 5; LT-157's evidence-gate still applies). Also make `runScanLeafOnce`'s summary dedupe against findings already seen so a corpus re-fire reads "0 new". **Shipped:** `NextAction` now takes a `llmfallback.RunDigest`; `buildOrchestratePrompt` renders (1) each leaf's `endpoint=` template when it has one, (2) a `recon facts` block (technologies with host+confidence, app-surface verdict, API spec, endpoint counts, JS-secret count, uniform-wall hosts, up to 5 truncated recon warnings; built by `pkg/orchestrator/digest.go`, unions tech across `recon.refresh`), (3) a `findings confirmed so far (distinct)` block (id/type/severity/target, capped at 25, overflow counted), and (4) history that collapses `Auto` turns to a count so a long fast lane can't push the model's own decisions out of the 10-turn window. The system prompt now says the tree, recon facts and findings list are ground truth and that a count in a turn summary is never evidence of a specific finding. `scan.leaf` results now read `N new finding(s) [id severity target; …], M repeat(s) of already-recorded findings ignored, K log line(s)`, and a repeat is neither appended to `Result.Findings` nor re-streamed via `OnFinding` (this also removes LT-166's *symptom* from the reported output — the redundant re-scan itself is still open). All prompt text is lab-neutral. Every turn is also logged via `OnLog` with the model's rationale (`turn N: scan.leaf <id> (why: …) — <result>`; also LT-170 (b)). **Live, crAPI:** before — turn 4 claimed "leaf-24 and leaf-23 already confirmed IDOR" from a bare `1 finding(s)` that was a re-fired info detection. After — the model's turn 1 picked the `mechanic_report` idor leaf (9 real `idor-*` findings), turns 3-5 read `0 new finding(s), 1 repeat(s) of already-recorded findings ignored`, and its rationales now cite what is actually on the findings list ("the sibling …/mechanic_report endpoint already confirmed 9 high-severity IDORs" — true, and grounded; turn 5 misstates 9 as 8). Turn 2 chose an `authbypass` leaf that had no `protected_paths` and skipped, so the digest did not steer it away from a leaf recon had no candidate for (see LT-180). Tests: `TestBuildOrchestratePrompt_ShowsEndpointTemplateReconFactsAndFindings`, `…_EmptyDigestSaysSo`, `…_DigestSectionsAreBounded`, `…_AutoTurnsCollapseToACount`, `TestRun_ModelSeesReconDigest`, `TestReconDigest_*`, `TestScanLeafSummary`, `TestDispatchScanLeaf_RefiredFindingIsNotRecordedTwice`. **Not done:** a per-turn "new vs already-known" flag on each digest finding, an endpoint list in the recon digest, and any A/B measurement of whether the richer prompt changes leaf choice (one crAPI run is anecdote, not an eval).
- **LT-173 (✅ fixed 2026-09-21, branch `feat/llm-finding-capability-phase0`; original diagnosis below) — one LLM stall kills an otherwise healthy run; the decision call has no output cap.** vAPI: turn 9's `NextAction` timed out at 4m0s, retried once, timed out again → `Run` returned `orchestrator: NextAction: … context deadline exceeded`, exit=1, with 10 findings in hand and 13 leaves still pending (`triage.rank` had run once on turn 8). crAPI's turn 5 timed out the same way (4m0s). `chatRequest` (`pkg/llmfallback/client.go:214`) is `{model, messages, temperature}` only — **no `max_tokens`, no reasoning-effort control** on a ~150-token JSON decision, so a reasoning-capable model can burn minutes on hidden reasoning tokens (the likely cause of LT-165's 60-150s+ latency, not just prompt size). **Fix:** (a) pass `max_tokens` (~600) and, where the provider supports it (OpenRouter's `reasoning` object), low/disabled reasoning effort for the orchestrator's decision calls — verify per-model support before relying on it; (b) on a `NextAction` failure after its one retry, *degrade* rather than error-exit: fall through to LT-172's fast lane (or stop cleanly, exit 0, "LLM unavailable — N leaves left undispatched") and still run `triage.rank`. Matches the standing preference for logged-warning-over-blocking on unattended paths. **Shipped:** (a) `NextAction` runs under an output envelope — `max_tokens` 2048, OpenRouter `reasoning: {effort: "low"}` (frontier tier only; overridable with `HACKERFIVE_DECISION_REASONING_EFFORT`, empty = send no `reasoning` field), and a 120s per-attempt deadline instead of 240s (a stalled call now costs 4 min including the client's one retry, not 8). `max_tokens` is deliberately generous because on most providers it covers hidden reasoning *and* the answer (OpenRouter's own docs), so a tight cap on a reasoning model comes back empty with `finish_reason: "length"`; that case is now an error (`errTruncatedResponse`, cost still counted) rather than an empty decision. (b) After `MaxConsecutiveLLMFailures` (2) consecutive failed decision calls `Run` stops asking the model, runs whatever the fast lane can still do, and ends cleanly with `Result.Degraded` set (reason plus how many leaves were left because they need a decision) instead of returning an error with findings in hand; a cancelled context still errors, and one failure followed by a success resets the count. **Live probe** (`TestLive_DecisionEnvelope`, gated on `HACKERFIVE_LIVE_LLM=1`, 2-3 trials per arm so directional only): `deepseek/deepseek-v4.1-flash` mean 12.6s → 7.7s and ~40% cheaper, 2/2 valid decisions in both arms; `openai/gpt-5.6-luna` 3.3s → 2.7s, 3/3 valid in both. **Not reproduced:** the 4-minute stall itself — neither model stalled on this small prompt, so whether the cap *prevents* the stall is unproven; the degrade path is what guarantees a stall no longer kills a run. Tests: `TestCompleteWith_*`, `TestDecisionCallOpts_*`, `TestRun_ModelFailsRepeatedly_DegradesInsteadOfErroring`, `TestRun_Degraded_CountsLeavesThatNeededADecision`, `TestRun_SingleTransientModelFailure_IsRetriedNotDegraded`, `TestRun_NonConsecutiveModelFailuresDoNotDegrade`, `TestRun_ModelErrorWithCancelledContext_StillErrors`.

- **LT-169 (open, design) — Wave 2 is port-blind for everything but the seed, so a shared host cross-contaminates facts (the real root cause behind LT-167's symptom).** With a bare-host scope and target `localhost:3000`, recon reported **Apache 2.4.25 / PHP / MySQL** — DVWA's stack on ports 80/3306 — as Juice Shop's: the bare `localhost` scope entry is added to httpx's input (default ports) and naabu sweeps top-100 ports of the host, then every `HostFact`/`TechFact`/`PortFact` is keyed by hostname only (`PlanNode.Target` is hostname-only end to end — see LT-167's own note on why threading a port through the tree was rejected). **LT-190 — built and live-verified 2026-09-22, on the user's explicit "yes, build it" — with a real detour worth recording.** The first attempt was exactly the plan above: add a backtick alternative to `jsQuotedStringRe`'s regex, normalize a resulting `${...}` interpolation to `<name>`/`{name}` the same way LT-186 already treats a literal `<orderId>` segment. Traced by hand: a completely unrelated template literal ~256KB earlier in the same bundle — Angular Material's own internal CSS-in-JS calc() logic, `` `calc(${this._currentDirection===`rtl`?`-1`:`1`} * (${`${a+l}px`} + ...` `` — nests a template literal three levels deep inside its own `${...}`. A flat regex has no way to track that nesting (regular languages fundamentally can't recognize balanced/nested delimiters); the "capture up to the next backtick" alternative paired the *closing* backtick of an unrelated, much-earlier literal with the *opening* backtick of `/rest/basket/${e}`, silently consuming it as part of a bogus match — and once one pairing desyncs, every later backtick pairing in the file does too. Raising the regex's length cap didn't fix it (Go's RE2 caps `{m,n}` at 1000 as it is, and the desync's cause was nesting, not length); an escape-aware version of the same regex didn't fix it either, for the same reason.

Two design options were weighed: (a) grow `Scope`'s domain-entry format with an optional `:port` suffix, or (b) have `dispatchReconRefresh` validate a fresh `target` against the plan tree's own already-established host:port set instead of deferring to the coarser file-level `Scope`. Option (b) turned out to be far more expensive than it looked: `pkg/registry`'s whole `PlanNode.Target` convention is hostname-only end to end (`newEndpointLeaf`, every host node built in `decisionengine.go`) — the actual scheme+port is reconstructed only at dispatch time, from the original `recon.ReconResult`'s endpoints (`reconHostBaseURL`), never stored on the tree itself. Threading port-awareness through the tree just for this one guard would have meant touching dozens of leaf-construction sites for no other benefit. **Fixed via (a) instead**: `scope.Scope`'s domain entries (`domainEntry{pattern, port}`) now accept an optional trailing `:port` (parsed via `net.SplitHostPort`, so a bare unbracketed IPv6 entry is correctly left alone rather than misparsed); `Allowed` compares it against the target's own port (defaulted to 80/443 by scheme when the target omits one) only when the entry specifies one — an entry with no port keeps matching any port, so every scope file written before this fix keeps working unmodified. `dispatchReconRefresh` itself needed no change: `recon.Run`'s existing top-of-function `Scope.Allowed` check (`recon.go:445`) now genuinely catches the drift once the scope file pins a port. `tests/eval`'s `hostOnly()` helper (renamed `hostScopeEntry`, used by both `agent_eval_test.go` and `orchestrator_eval_test.go`) now writes `host:port` instead of a bare host, closing the exact reproduction vehicle this bug was found through. New tests: `TestAllowed_PortPinnedEntry_RejectsOtherPortsOnSameHost`, `TestAllowed_PortlessEntry_StillMatchesAnyPort`, `TestAllowed_PortPinnedWildcardEntry`, `TestEntries_PortPinnedEntry_RoundTrips` (`pkg/scanner/scope/scope_test.go`). Note this is opt-in: an operator's existing bare-hostname scope entry is unaffected until they actually add `:port` — the fix gives `--scope` the vocabulary to express a port boundary, but doesn't retroactively tighten a scope file nobody has edited.

**Baseline finding inventory (20 findings post-dedup, before the fixes above):** `www` got WP-user-enum + 2 FPs; `soporte` got one lucky corpus hit; `cloud02` got its Nextcloud findings but `cloud01` (identical) got 0 — all from LT-113. `erp`/`cloud01`/`gateway` got 0 findings each. `wiki` produced a false `misconfig-exposed-path-swagger-ui.html` (the scan-side face of LT-104). Missed vs. the hand-verified table: Dolibarr on `erp`/`ixn` (LT-113), Webmin on `gateway:10000` (port never scanned), phpMyAdmin on `chasqui03` (host never discovered, LT-111).
