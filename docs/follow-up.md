Without it, `hackerfive agent` auto-appended the full ~2,500-tag-scoped synced corpus, and vAPI's already-documented "full corpus hangs against its dev server" gotcha (`docs/20-setup-testing-targets-macos.md`) made a single `scan.leaf` take 4+ minutes — with `Config.MinIterations` forcing several such turns, the run blew the harness's timeout with 0 tool_calls ever completing (an infra artifact, not a reasoning miss). Fixed by adding `OrchestratorScenario.Templates` and wiring `--templates` into the dispatched args; vAPI set to `"./templates/"`, crAPI to `templatesDir()` — both mirroring their deterministic-scenario counterparts. Live-verified: vAPI's orchestrator run went from timeout/0 findings to 4/5 (matching the deterministic baseline exactly).
  2. ✅ fixed — the per-scenario context timeout was a flat 10 minutes, copied from `TestAgentEvalHarness` (MCP-plan mode) before `Config.MinIterations` (LT-162's own fix) existed. Live-verified against crAPI: individual `NextAction` calls against `deepseek/deepseek-v4.1-flash` took 60-150s+, and `MinIterations`'s forced floor of dispatched turns (plus any rejected-stop retries, each its own `NextAction` round trip) pushed total wall-clock past 10 minutes on a target with more candidate leaves to consider than vAPI/DVWA/Juice Shop. Raised to 20 minutes in `orchestrator_eval_test.go`.
  3. **✅ fixed 2026-09-19** — found via the same crAPI run: it was killed by the (then-10m) timeout mid-run, after a real `misconfig-exposed-path-.env` (high severity — crAPI's own `.env` file, containing real secrets, is genuinely publicly exposed) had already been surfaced live via `OnLog`/turn history, but `hackerfive agent`'s CLI only printed its final `Result` JSON after `orchestrator.Run` returned cleanly — a killed process (this harness's timeout, but equally a real Ctrl-C, OOM, or host reboot) discarded every finding already discovered that run, with no partial output at all. Fixed by changing `cmd/hackerfive/agent.go`'s stdout/`--output` contract from one pretty-printed `Result` document written only at the end to a JSON-Lines stream (new `agentStreamEvent`/`agentEventWriter`): a `{"type":"finding",...}` line is written and flushed the instant `Config.OnFinding` fires (already called synchronously per real detector match, per `pkg/planexec.ExecOptions.OnFinding`'s own doc comment), and a final `{"type":"result",...}` line carries the complete `orchestrator.Result` once `Run` returns (with `error` set if `Run` itself errored, so a partial-but-real `Result` on a `NextAction` failure is never dropped either). `os.Create`/`os.Stdout` are both unbuffered Go-level writers, so a completed `Encode` call is durable in the OS pipe/file the instant it returns, regardless of what kills the process afterward. `agentEventWriter` serializes concurrent writes (a leaf's scanner engine can report findings from more than one worker goroutine) — covered by `cmd/hackerfive/agent_test.go`'s new `TestAgentEventWriter_*` tests (streaming order, a `Run`-error result event, and a 50-goroutine concurrent-write test asserting every line still parses independently). `tests/eval/orchestrator_eval_test.go` was updated to scan stdout line-by-line and collect `finding` events (falling back to them when a killed run's `result` event never arrives) instead of requiring one whole-buffer `json.Unmarshal` — this is what makes a killed run's real findings actually count in the FP/FN table (LT-166's redispatch issue no longer implies "0 findings observed" the way it did before this fix; see LT-166 for the actual redispatch root cause, still open).

- **LT-164 (✅ fixed 2026-09-19)** — crAPI's orchestrator run found 0/2 expected prefixes (vs. the deterministic baseline's 1/2, LT-163) because recon never discovered `/workshop/api/mechanic/mechanic_report` on its own (the deterministic `Scenario` is handed it directly via `--endpoint`). Investigated live against the real container before assuming a fix: crAPI does **not** expose a per-service OpenAPI/Swagger spec at any conventional path, authenticated or not (`/identity/`'s Spring gateway 401s *every* path under its prefix, real or not, before route resolution even runs — confirmed by diffing a known-real vs. a made-up path, both 401) — so extending `probeCommonPaths`' spec-walk to retry under discovered prefixes, the originally-proposed fix, would not have helped. The real, live-verified gap: crAPI's React bundle builds its request URLs at runtime from separately-declared string constants (`ig="workshop/"` + `sg.GET_SERVICE_REPORT="api/mechanic/mechanic_report"` + `"?report_id="+id`), and neither piece alone is endpoint-shaped enough for `extractJSEndpoints` (`jsstatic.go`) to ever see it. Fixed by adding a join pass (`extractJSPathJoinParts`/`buildJSJoinPairs`/`verifyJSJoinCandidates`, `pkg/recon/jsstatic.go`) that reconstructs prefix+base(+query-suffix) candidates from a bundle's own constants and live-verifies each one (bounded to `maxJSJoinProbes`) before emitting it as a `js-static-joined` EndpointFact — critically, verification diffs each candidate against a **per-prefix canary** (`fetchJSPrefixCanary`), not just a status-code allow-list, specifically because identity/'s blanket-401 behavior would otherwise "verify" a wrong prefix+base combination just as confidently as the real one, reintroducing the exact multi-candidate ambiguity this step exists to resolve (live-verified: an earlier version without the canary diff produced both `identity/api/mechanic/mechanic_report` and `workshop/api/mechanic/mechanic_report` as "verified," the canary diff correctly keeps only the real one). Two more real, unrelated bugs surfaced and were fixed along the way, both pre-existing and both silently capping recon on *any* real-world SPA, not just crAPI: (1) `maxJSStaticBodyBytes` truncated a captured JS body at 512 KiB — crAPI's single-file CRA bundle is 1.65 MB with its route constants sitting at byte ~1.6M, entirely past the old cap (raised to 4 MiB); (2) `runKatana`'s JSONL scanner (`crawl.go`) had a 1 MiB `bufio.Scanner` max-token-size — once the JS bundle's body pushed a single JSONL line past it, `Scan()` silently returned false and **the rest of that crawl's output, not just that line, was discarded with no error surfaced**, which is why `main.js` never appeared in `hackerfive recon`'s own endpoint list even though a manual `katana` invocation with identical flags found it every time (raised to 8 MiB, plus a new warning on `scanner.Err()` so a future overflow is loud, not silent). Live-verified end-to-end against the real crAPI container: `hackerfive recon --recon-depth full` now surfaces `js-static-joined http://.../workshop/api/mechanic/mechanic_report?report_id=` as a single, unambiguous candidate. `tests/eval/orchestrator_run.go`'s crAPI scenario was also switched from `Depth: "active"` to `Depth: "full"` — Wave 3 (crawl + JS-static analysis, where this whole fix lives) never runs below `"full"`, so the scenario couldn't have exercised this fix at all otherwise; every other `OrchestratorScenario` stays at `"active"` since none of their expected findings need Wave 3. **The candidate-generation gap itself is closed and confirmed**: with `Depth: "full"`, one orchestrator eval run did dispatch a real `scan.leaf` against the recon-discovered endpoint and produced 5 genuine `idor/high` findings (`report_id=1..5`, "otherToken retrieved real user data ... does not match the established denied-access baseline"). The eval scenario still doesn't pass end-to-end, though, for a separate, newly-discovered reason — see LT-166.

- **LT-165 (item 1 ✅ fixed 2026-09-19, item 2 deliberately not attempted)** — `pkg/llmfallback.Client.NextAction` calls against `deepseek/deepseek-v4.1-flash` (via OpenRouter) are slow in practice: 60-150s+ per call, live-observed during LT-162/163's re-verification. This is what made `Config.MinIterations`'s forced turn floor (LT-162's own fix) push crAPI's orchestrator run past a 10-minute budget (LT-163 raised the eval harness's timeout to compensate, but the underlying latency itself was unaddressed). Two independent angles were named:
  1. ✅ fixed — `buildOrchestratePrompt` (`pkg/llmfallback/orchestrate.go`) already capped turn *history* at `maxHistoryTurnsInPrompt` (LT-162's fix) but rendered the full plan-tree leaf list uncapped on every call — on a target with many leaves (crAPI's tree is larger than vAPI/DVWA/Juice Shop's), this was a real, still-uncapped contributor to prompt size (the tool catalog itself is a fixed ~6-entry list, negligible either way, so only the leaf list needed a cap). New `boundedLeavesForPrompt` caps the rendered leaf list at `maxLeafNodesInPrompt` (80), keeping every actionable (`StatusPending`/`StatusUnresolved`) leaf visible first — those are the only ones a `node_id` could usefully target this turn — and dropping an already-settled leaf (done/vetoed/escalated) first when the cap is hit; if even the actionable set alone exceeds the cap, it's truncated too (an omitted actionable leaf becomes visible on a later call once earlier ones resolve), rather than growing the prompt further. Tests: `TestBoundedLeavesForPrompt_UnderCap_ReturnsAllUnomitted`, `TestBoundedLeavesForPrompt_OverCap_KeepsActionableDropsSettledFirst`, `TestBoundedLeavesForPrompt_ActionableAloneExceedsCap`, `TestBuildOrchestratePrompt_CapsLeafListAndNotesOmission` (`pkg/llmfallback/orchestrate_test.go`).
  2. **Deliberately not attempted** — skipping `NextAction` outright when the tree has exactly one viable leaf was considered but not implemented: the catalog always also offers `recon.refresh`/`triage.rank`/`stop` alongside `scan.leaf`, so "one viable leaf" doesn't actually mean "one viable action" — forcing `scan.leaf` on that one leaf would remove the model's legitimate choice to triage already-collected findings, refresh recon first, or stop (e.g. a leaf that already escalated through its attempt/spend ceiling shouldn't be force-dispatched again). This is a real latency lever but a behavior-risking one without live eval data to confirm it doesn't regress recall — left for a future pass with an eval run to validate against, not guessed at here.

- **LT-166 (open — a real related bug fixed 2026-09-19, exact crAPI root cause still unconfirmed)** — live-verified 2026-09-19, immediately after LT-164's fix: with `Depth: "full"`, the crAPI orchestrator eval run dispatched `scan.leaf` against `.../workshop/api/mechanic/mechanic_report?report_id={{id}}` and got 5 real `idor/high` findings — but the *identical* dispatch (same URL, same `report_id=1..5`, same "5 raw finding(s)" summary) then repeated two more times later in the same run, each a full ~1m20s re-scan, before the run exhausted the harness's 20-minute timeout and was killed. At the time this was compounded by LT-163 item 3 (now fixed — see above): all 3 rounds of real findings were lost from the final output despite the detector genuinely working. Two candidate causes were ruled out by code reading, not just inspection: (1) `pkg/orchestrator`'s dispatch guard (`dispatchScanLeaf` rejects a non-pending/non-unresolved leaf), `planexec.RunPlan` (marks a dispatched leaf `StatusDone` unconditionally via `ApplyLeafUpdate` immediately after execution), and `PlanTree.Find`/`ApplyLeafUpdate` (both operate on the same live node via the same mutex, no staleness possible) form a provably-consistent chain — a single leaf ID genuinely cannot be re-dispatched by `dispatchScanLeaf` once `RunPlan` has marked it done, ruling out "the same node_id re-selected after a status bug." (2) The `seenAssetURL` asset-dedup fix (LT-164) was confirmed to be **not the mechanism**, and not just unconfirmed: `pkg/recon/suggest.go`'s `idorCandidatesAndSeeds` dedups by the final `{{id}}`-templated string (`seen[tmpl]`) *before* `registry.Resolve`'s LT-91 fan-out (`decisionengine.go` line ~1483) ever iterates candidates to build leaves — so even 3 duplicate raw `EndpointFact`s for the same URL (which `seenAssetURL` now prevents anyway, as good practice) would already have collapsed to exactly one leaf. **Diagnostic added (not yet live-confirmed):** `pkg/orchestrator.warnDuplicateLeafTargets` now runs once right after the initial tree is built and logs (via `OnLog`, which — since LT-163 item 3's fix — now survives a killed run in `hackerfive agent`'s streamed stdout) any set of 2+ leaves sharing identical Detector+Target+EndpointTemplate, naming their IDs. Unit-tested (`TestWarnDuplicateLeafTargets_*`, `pkg/orchestrator/orchestrator_test.go`). The next live crAPI eval run, even if killed by the timeout again, will show directly via a streamed `OnLog` line whether duplicate leaves exist. Until closed, a real recon-discoverable finding can still cost 3x its true budget on a target that triggers this.
  **A real, previously-unfound instance of "a different leaf ID resolving to an identical dispatch" was found and fixed 2026-09-19** (via a fresh static-code-reading pass, not a live crAPI re-run — no Docker/API key available in this environment; the exact crAPI trigger therefore remains unconfirmed, and this fix is reported honestly as *a* closed gap in the dedup chain, not *the* proven root cause). `idorCandidatesAndSeeds`'s two candidate sources formatted the *same* (path, key) two different ways: the per-endpoint `idShapedQueryCandidate` pass (an ID-*named* key, e.g. `report_id`) preserves every sibling query param in its template (`"?report_id={{id}}&foo=bar"`), while the separate LT-83 `numericQueryIDCandidates` pass (an unnamed-but-varying numeric key) drops all sibling params (`"?report_id={{id}}"`) — for a key whose name happens to also look ID-shaped *and* whose value varies across ≥2 observations, both passes fire and produce two different template strings for what is really one identifier position, defeating `seen[tmpl]`'s exact-string dedup and fanning out two `idor` leaves (LT-91) that dispatch an effectively identical check — precisely the class of bug LT-166 hypothesized, just located in candidate generation rather than in `Resolve`'s fan-out itself. **Fixed:** `numericQueryIDCandidates` (`pkg/recon/suggest.go`) now returns a `queryIDKey{path, key}` struct instead of a pre-formatted string; `idShapedCandidate`/`idShapedQueryCandidate` now also return the matched query key; `idorCandidatesAndSeeds` records each per-endpoint query match's `(path, key)` in a `seenQueryKey` set and skips a `numericQueryIDCandidates` result already covered by it, before ever formatting/comparing template strings. `SuggestSQLiTargets`'s own `numericQueryIDCandidates` caller was updated to use the new struct fields directly instead of parsing the old formatted-string return (a simplification, not a behavior change — it already merged both signals' params into one path-keyed target, so it was never exposed to this bug the way `idorCandidatesAndSeeds`' per-leaf fan-out was). Test: `TestSuggestIDOREndpointCandidates`'s new "an id-named query key varying across >= 2 observations must not also fan out via the LT-83 numeric path" case (`pkg/recon/suggest_test.go`) reproduces the exact two-source collision and asserts exactly one, sibling-preserving candidate survives.
