Open:
- **`--rate-limit` default (50 req/sec) is too aggressive as a default** — recommended conservative default is 5-10 req/sec. Set in Phase 1a, not revisited since.
- **No `--include-raw-evidence` opt-out** — evidence redaction is always-on, not togglable. Minor, not yet needed.
- **Baseline-mode account provisioning** has no general guidance for a real bounty/VDP target — only lab-target-specific steps exist ([20-setup-testing-targets.md](20-setup-testing-targets.md)).
- **Self-hosted `interactsh-server` still not stood up.** The public-server default (retry-hardened, `pkg/oob`) covers scanning your own sites; a private server is still the right choice for a real third-party engagement — the server operator sees the target's IP/timing either way.
- **nuclei's interactsh_ OOB support (2026-09-04, see Template Engine & Detection Backlog below) changes the traffic-footprint profile of that same leak tradeoff**: the ssrf detector's own OOB check polls once per SSRF-param check; `oob.Poller` (shared across `nuclei.Executor`) instead runs a continuous background poll every 2s for as long as any interactsh_ template has fired during the scan — a real, currently-unbounded increase in sustained traffic to a configured server (default-public or self-hosted) for a full-corpus scan, not just brief poll blips. Not mitigated here (no idle-pause); worth revisiting if this matters for a specific engagement's OPSEC posture.

## Detection Coverage — Protocol/Capability Expansion

Assessed against [02-architecture-and-tech-stack.md](02-architecture-and-tech-stack.md)'s `code:`/`javascript:`/`headless:`/`file:` template-rejection boundary and the read/enumerate-only rule.

| Capability | Verdict | Why |
|---|---|---|
| TCP | Add | Already a Nuclei protocol type, deferred (not rejected) from the HTTP-only parser. Banner grab / port ID, read-only. |
| TLS/SSL | Add | Passive checks (expired/weak certs, deprecated protocols, weak ciphers) via stdlib `crypto/tls`, no new dependency. |
| JS static analysis | Add | Crawl served JS for hardcoded secrets/endpoints (LinkFinder/SecretFinder-style) — read-only, feeds IDOR/misconfig. |
| Headless/DOM (Chromedp) | Keep scoped | Already planned for DOM XSS validation, sandboxed, first-party-only — doesn't relax the `headless:` template rejection for community templates. |
| OOB blind RCE verification | Add | Extend the SSRF Interactsh/OOB pattern to RCE: prove execution via callback, never run attacker-meaningful commands. |
| Literal command execution on target | Reject | Crosses into exploit; conflicts with read/enumerate-only and most program authorization. OOB verification gets the same detection value without it. |

TCP/TLS/JS-static are natural next additions — same architecture, no new dependency, no policy conflict. The command-execution boundary is worth stating explicitly in doc02 alongside the existing template rejections.

- **`body_N`/`header_N`-as-a-`part:`-value gap, plus the genuine `path:`-multi-request correlation refactor.** ✅ done 2026-09-04. Real corpus measurement first, and it reshaped the whole item: of 1,183 rejected templates, 246 hit "unsupported part" on an indexed name (`body_2`/`header_2`/`content_type_2`) and 33 hit "unknown identifier" on the DSL form (`body_2` used inside `dsl:` rather than `part:`) — but splitting those 246 by request shape showed **239 of them were already `raw:`-based templates whose `body_N`/`header_N` correlation already worked via `dsl:` identifiers** (see the prior `content_type_N`/`duration_N` entry above) — the only gap was that `matcher.ValidPart`/`Part()` never recognized an indexed `part:` *name* at all, rejecting e.g. `CVE-2014-4592.yaml`'s `part: body_2` word matcher outright regardless of request shape. Fixed with zero execution-model risk: `matcher.IsIndexedPart` (a `body_N`/`header_N`/`content_type_N` name pattern) + `ValidPartWithContext` (accepts an indexed name only when the caller's `dsl.Context.Vars` already carries that exact key — reuses the same per-request "how many probes fired" bound `dsl:` validation already established) + `Part()`'s default case falling back to `r.ExtraVars[part]` — `tryRawIteration` already populated exactly those keys, so no executor change was needed for this half at all. The genuinely small remainder (7 `part:`-shaped + 33 `dsl:`-shaped = 40 real templates, not ~220) needed the real correlation refactor: a plain `path:`-based request (no `raw:`) whose matchers/extractors reference an indexed identifier (real example: `CVE-2012-3153.yaml`'s `contains(body_1, "Reports Servlet")` / `!contains(body_2, "<html")` across its 2 `path:` entries). Implemented as an **opt-in flag, not a behavior change to the default path**: `loader.go`'s `usesPathCorrelation` scans a request's matchers/extractors (both `dsl:` expressions via a word-boundary regex, and `part:` values via `IsIndexedPart`) at load time and sets `HTTPRequest.pathCorrelated` only when `len(Raw) == 0 && len(Path) > 1` *and* an indexed reference is actually found — every one of the ~9,000+ other multi-path templates (which rely on today's independent try-each-path-until-match behavior) is completely unaffected, verified both by the full existing test suite passing unchanged and by a new explicit regression test (`TestExecutorRun_IndependentMultiPath_EachPathReportsSeparately`). A flagged request runs through new `runPathRequestCorrelated`/`tryPathCorrelatedIteration` (`executor.go`) — structurally a straight port of `tryRawIteration` to fire every `Path` entry instead of every `Raw` entry, binding the same `body_N`/`header_N`/`status_code_N`/`content_type_N`/`duration_N` keys and evaluating matchers once against the last entry. **One more real gap found via re-measurement, not anticipated up front**: several real templates (`CVE-2023-1362.yaml`, `yonyou-nc-baseapp-deserialization.yaml`) reference the "`_1`"-suffixed form (`status_code_1`, `body_1`) on a *genuinely single-path* request — real Nuclei's DSL always accepts `_1` as a synonym for the bare identifier even with nothing to correlate against. Fixed by always aliasing `body_1`/`header_1`/`content_type_1`/`status_code_1`/`duration_1` to the bare values in `tryPath` itself (no correlation firing needed — there's only ever one response), and widening `loader.go`'s `indexedDSLContext` to seed index-1 dummy vars for any single-path request, not just when `len(path) > 1`. Real corpus measurement: 1,183 → 923 rejected (260 templates newly loadable — 256 from the two combined fixes, 4 more from the `_1` alias). **Remaining 5 real `identifier_N_unknown` rejections are a different, smaller, distinct gap, deliberately not chased here**: real Nuclei's `flow:` templates number `_N` *globally across separate `http:` request blocks* (e.g. `yonyou-u8-sqli.yaml`'s `http[1]` matcher references `duration_2` where `_2` means "the flow's 2nd fired request block", not "the 2nd probe within this block") — a materially different cross-block indexing model than the same-block correlation this pass implements; one further sampled rejection (`CVE-2021-45968.yaml`) turned out to be an unrelated raw-request-smuggling technique (3 literal HTTP request lines concatenated into one `raw:` entry, expecting multiple pipelined responses) this project's `http.Client`-based executor has no way to honor regardless. Logged as a new, separate, much smaller follow-up rather than folded in.
- **Multi-key `payloads:` (attack: pitchfork/clusterbomb/batteringram).** ✅ done 2026-09-04. `pkg/template/nuclei/schema.go`'s `resolvePayloads` (was `resolvePayload`) now returns every substitution pass for 2+ payload keys instead of rejecting them; `pitchforkIterations` (zip, shortest-list length), `clusterbombIterations` (full Cartesian product, odometer-style), `batteringRamIterations` (one shared list broadcast into every key). Semantics are Burp Intruder's own well-documented attack-type definitions (Nuclei borrowed the naming directly) confirmed against real corpus examples before implementing, not guessed — e.g. `zabbix-default-login.yaml`'s `clusterbomb`/`max-request: 2` matches `2×1×1` exactly. **Correction to the 2026-09-04 "485 templates" estimate logged against this item earlier the same day**: that number conflated genuine multi-key rejections with the separate file-based-`payloads:` gap (both hit the old code's blanket `len(Payloads) > 1` check, or now the per-key file-based check, in a way the original bucket-counting couldn't separate) — direct YAML inspection puts the real split at 238 multi-key-only, 248 file-based-only, 3 both. Real corpus measurement: 1,634 → 1,434 rejected (200 templates newly loadable — short of the 238 "should now load" figure because some hit a second, still-open gap behind this one, e.g. real pitchfork example `CVE-2019-15642.yaml` also uses `part: body_2`).
- **File-based `payloads:` (WordPress-version-detection pattern).** ✅ done 2026-09-04. Real count 251 (not the old "240" estimate), and simpler than described: real inspection of upstream's `http/technologies/wordpress/plugins/*.yaml` (237 of the 251) showed each is a *single-value* file (a plugin's current version string), not a real wordlist — the pattern is `compare_versions(extracted_version, concat("< ", loaded_value))`, reusing the already-working same-request extractor→matcher binding, no new correlation mechanism needed. Three pieces: (1) `pkg/templatesync.SupportDirs` (`["helpers"]`) sparse-checks-out upstream's `helpers/` wordlist directory alongside the `http/` categories — the synced corpus had never fetched it at all, a real prerequisite the original backlog description didn't call out; (2) `schema.go`'s `readPayloadFile` resolves a template's file-based `payloads:` value relative to the corpus root (`Template.sourceDir`, populated at load time), one value per non-empty line, with a path-traversal guard; (3) `dsl.go` gained `concat()` (variadic string/int concat, matches every real corpus call shape checked first). **Two real bugs found and fixed along the way, both by testing the actual pattern end-to-end, not just confirming the template loads**: (a) a request's own `payloads:` variable (e.g. `last_version`) was never bound into the DSL-visible `ExtraVars` in either `tryPath` or `tryRawIteration` — only used for request *rendering* — so a template referencing its own payload variable directly in a `dsl:` matcher (the WP-version pattern's entire premise) silently produced zero findings even when genuinely vulnerable; affected both new file-based and the already-shipped multi-key payloads, undetected until now since no earlier test exercised a bare payload-variable DSL reference. (b) `yaml.v3`'s `node.Decode(&[]string{})` silently drops a `null` list entry rather than decoding it as `""` (confirmed: `[null]` decodes to a zero-length slice) — broke the one real corpus template using a legitimate blank-credential default-login check (`softether-vpn-default-login.yaml`: `password: [null]`); fixed via `decodeStringSequence`, which decodes `!!null` as an explicit empty string. Real corpus measurement: 1,434 → 1,183 rejected (251 templates newly loadable — the full file-based-only count, no shortfall this time).
- **`flow:` cross-block `_N` indexing (~4-5 templates).** Surfaced 2026-09-04 while re-measuring the `body_N`/`header_N`-as-`part:`-value fix above. Real Nuclei's `_N` suffix in a `flow:` template (`flow: http(1) && http(2)`, etc.) numbers *globally across every fired `http:` request block*, not per-block — e.g. `yonyou-u8-sqli.yaml`'s `http[1]` (a single-`raw:`-entry block) references `duration_2`, meaning "the flow's 2nd fired request", not "the 2nd probe within this block". This project's `body_N`/`header_N`/etc. binding is entirely per-block (`tryRawIteration`/`tryPathCorrelatedIteration` each reset their own index counters), so a cross-block reference is still "unknown identifier". Small (only a handful of real corpus hits) and a genuinely different indexing model than the same-block correlation just implemented — not a small addition to that work, a separate one: would need `runFlow` to thread a running global counter (or full per-request history) across its `http(N)` calls instead of each call rendering independently. **Confirmed the same gap covers `interactsh_protocol_N`/`http_N_location` too**, found while measuring the interactsh_ OOB item below: exactly 2 real templates (`CVE-2023-50094.yaml`'s `contains(interactsh_protocol_2, "dns")`, another sampled hit) reference an indexed `interactsh_protocol_2` the same way, plus 2 more referencing `http_1_request`/`http_3_location` (extractor-side cross-block reads) — same fix, not chased separately.

- **`interactsh_*`/OOB support for nuclei templates.** ✅ done 2026-09-04. Wires the existing `pkg/oob` Interactsh-protocol client into `pkg/template/nuclei`, previously entirely unimplemented (`matcher.ValidPart`'s doc comment used to name `interactsh_protocol`/`interactsh_request`/`interactsh_response` as explicitly out of scope). Real corpus measurement first: 532 templates reference `{{interactsh-url}}`/`interactsh_protocol`/`interactsh_request`/`interactsh_response` (larger than the doc's prior "~350" estimate), 519 of them rejected at load — 493 on the explicit "out-of-band, not supported" matcher/part error, the rest on the DSL form ("unknown identifier"). After this work: 519 → 31 rejected (488 net newly-loadable).
  - **Design**: `HTTPRequest.usesInteractsh` (load-time flag, same pattern as `pathCorrelated`) gates a per-request-execution `prepareOOB`/`awaitOOB` pair in `executor.go`: `prepareOOB` (called once per `tryPath`/`tryRawIteration`/`tryPathCorrelatedIteration` call — i.e. once per payload iteration, so every entry within one correlated multi-entry block shares the same probe) generates a fresh correlation host+nonce via `oob.Client.NewPayloadHost` and injects it as the `{{interactsh-url}}` render variable; `awaitOOB`, called once every entry in that iteration has actually fired, blocks up to `oobWaitTimeout` (6s) for a correlated callback and always returns all three `interactsh_protocol`/`interactsh_request`/`interactsh_response` keys (real values, or `""` on no callback) — never omits them, since `Part()`'s `r.ExtraVars` lookup for an unrecognized/absent part name used to fall through to the response body (the exact historical false-positive class `ValidPart`'s doc comment describes); `matcher.Part` also now special-cases these three to never fall through regardless of caller discipline (`TestMatcherPart_InteractshFallsBackToEmpty_NotBody`).
  - **New `oob.Poller`** (`pkg/oob/poller.go`): a single `Client` registration is shared across the whole `Executor` (and, since `Executor` is itself shared across the scan's worker-pool goroutines, across every concurrently-scanned target) — `Poll`'s "everything since last call" semantics meant an uncoordinated second `Poll` around the same time could silently steal an interaction a different, still-waiting goroutine needed. `Poller` centralizes every `Poll` behind one background loop (ticks every `oobPollInterval` = 2s once started) and a nonce→waiter channel map, so `Wait` is the only thing callers ever call.
  - **Lazy, opt-in registration**: `Executor.WithOOBServers` (wired from `scanner.Config.OOBServers` — the same `--oob-server`/`--no-oob` value the ssrf detector already uses, not a second config surface) only actually registers against a server (`ensureOOBPoller`, `sync.Once`) the first time a *loaded* template's request actually embeds `{{interactsh-url}}` — a scan whose `--templates` set never references it (the common case, e.g. the default curated set) never talks to an OOB server at all, default-public or not. `Executor.Close` (deferred once in `engine.go`) stops the poll loop and deregisters.
  - **Two real, related gaps found and fixed alongside**, discovered by trying to actually render+fire real sampled interactsh_ templates end to end, not just load them: (a) `vars.placeholderPattern`'s `\w+` regex cannot match a hyphen, so `{{interactsh-url}}` — the one common real Nuclei built-in with a hyphen in its name — used to pass straight through `Render` as the literal, unsubstituted text, no error; widened to `[\w-]+`. (b) `{{randstr}}` (a random-string cache-buster, paired with `{{interactsh-url}}` in ~51 of the 532 templates, e.g. real `CVE-2019-6799.yaml`) and `{{RootURL}}`/`{{Host}}` (40/6 templates) were entirely unimplemented ("undefined variable"); added `randstr()` (seeded once per `Run()`/`runFlow()` call, shared across every request in that template execution — matches real Nuclei's per-template-execution dynamic-variable scope) and `RootURL`/`Host` as `Render`-level aliases of `BaseURL`/`Hostname`.
  - **Known, accepted latency tradeoff, not solved here**: `awaitOOB` blocks inline, serially, once per interactsh_ template (this project's scan loop fires templates against one target sequentially — `engine.go`'s `Run`) — a longer, more generous wait would make a full-corpus scan (~500 interactsh_ templates) impractically slow. Real Nuclei instead fires every OOB-needing request across the whole scan first, then does one deferred correlation pass at the end — a materially bigger architecture change than fit this pass (this project's request-firing functions return a finalized match/Finding immediately, needed for extractor→chainVar propagation and flow gating). Logged here as the natural next OOB improvement if the current 6s-per-probe serial cost proves too slow in practice.
  - **Verification note (user's explicit request)**: every test added for this item (`tests/unit/nuclei_executor_test.go`'s `TestExecutorRun_InteractshCorrelation_*`, `tests/unit/oob_test.go`'s existing pattern reused) registers exclusively against a local `httptest.NewServer` fake Interactsh-protocol server (`newFakeOOBServer`, real RSA-OAEP+AES-256-CTR round trip, already established by `detector_ssrf_test.go`) — none construct an `Executor`/`Client` against a real `oast.pro`/`oast.live` or any other public server. Confirmed via `git diff` grep across every changed file: the only "oast."/"public" occurrences are prose in doc comments, never a URL passed to `WithOOBServers`/`NewClient` in code or tests.
  - **Remaining 31/532 rejections after this pass, categorized** (none interactsh-specific): `javascript:`/`tcp:` disallowed blocks (4, pre-existing intentional exclusion), `flow:` `if`/`set` constructs (4, pre-existing gap, table above), `location`/`set_cookie` unknown identifiers (8, pre-existing gap, table above), `xpath` extractor (2, pre-existing gap, table above), absolute-URI raw requests (2, pre-existing intentional restriction), `internal: true` outside `flow:` (2, pre-existing restriction), cross-block `interactsh_protocol_N`/`http_N_location`/`response_2` (4, folded into the `flow:` cross-block item above), and 3 one-off template-specific oddities (an unbound `agent_name` identifier, a `base64_decode()` call against a load-time dummy that isn't valid base64, one flow: script parse error) not worth chasing individually.
- **P1-5 `techRules` coverage.** Partially done 2026-09-04: `woocommerce` → `misconfig` added. `contact-form-7` and other plugin-specific coverage come from P1-3's slug-tag matching instead (no techRules row needed — these are plugin CVEs, not a generic capability). ### P2 — LLM leverage & ergonomics

All six items done 2026-09-04 — see [15](15-implementation-plan-ph6.md) Step 2's P2 addendum for full detail.

- **P2-2 Feed `ResolveLeaf` structured data.** ✅ `registry.Resolve` now returns a second value, `map[string]LeafContext` (the originating `TechFact`/`PortFact`/correlated endpoints, keyed by leaf ID), which `ResolveLeaf`/`buildLeafPrompt` read directly instead of regexing `leaf.Rationale`. Closed a real, live gap: P1-2's port leaves use an entirely different Rationale sentence shape the old regex never matched at all, so tag ranking got zero signal for every port-open unresolved leaf. The regex (`techNameFromRationale`) stays as a fallback for a caller with no LeafContext (e.g. a cached webui tree — see below).
- **P2-3 Make `use_existing_tag` executable** (doc15 Open Issue #2). ✅ `buildLeafPrompt` now lists ranked-relevant *templates* by exact `id: name` (`rankRelevantTemplates`, reusing P0-2's own tag-ranking), not shared tags — `RunPlan` can only dispatch a leaf whose `Detector` is a real capability name or `templatesync.Entry.ID`, never a bare tag, so a decision naming a tag used to be undispatchable in practice.
- **P2-1 `PlanFromRecon(ReconResult)` — a 4th `pkg/llmfallback` caller.** ✅ One local-tier-first call per plan run (not per leaf) proposing `{target, detector, rationale}` leaves beyond what per-fact matching found; `MergeLLMProposals` merges them in with two hard safety filters no other I4 caller needs: `Target` must already name a host node `registry.Resolve` itself produced (never a target the model invented), and `Detector` must be a real capability name or known template ID. **Deliberately not wired into the MCP `plan` tool's or webui's default flow** — `pkg/llmfallback`'s own package doc states I4 fires "only on a confirmed deterministic-decision-engine miss — never as a standing parallel path," and calling this unconditionally on every plan run would be exactly that. Wired only into CLI `plan --llm-assist` (P2-4), itself an explicit opt-in. Widening it to MCP/webui as a standing broader-coverage pass is a real option but changes that documented architectural principle — a call for whoever owns that tradeoff, not made unilaterally here. Redaction turned out lighter than assumed: `ReconResult`'s other fields were already designed to carry no raw response body/header/cookie data (doc91 §4); only `HostFact.Notes` (free-form WHOIS/ASN text) is dropped from the prompt.
- **P2-4 Wire I4 into CLI `plan` behind `--llm-assist`.** ✅ Calls `ResolveTreeLeaves` then `PlanFromRecon`/`MergeLLMProposals`, off by default (`plan`'s own zero-LLM-calls proof stays the default). **Not wired into `scan`**: `scan` requires `--detector`/`--endpoint` explicitly via `cfg.Validate()` already — there's no unresolved-leaf/field-miss concept for I4 to resolve there, so "wire I4 into scan" had no concrete meaning once inspected against the real command. `llmfallback.New()`'s degrade-not-hard-fail behavior was already true at every existing call site (`tools_triage.go`, `tools_plan.go`, `webui`) — the new CLI call site follows the same pattern.
- **P2-5 Index/corpus drift guard.** ✅ `templatesync.CountTemplateFiles` (cheap file count, not a full parse) + `IndexDriftWarning` compare `templates/index.json`'s entry count against real on-disk `.yaml`/`.yml` files across the same dirs `templates index` itself indexes from; `plan` warns to stderr when they're wildly out of sync (catches the real scenario: a stale index against an emptied/re-pointed synced directory). **Not wired into `scan`**: `scan` never reads `templates/index.json` at all (it loads `--templates` dirs directly, always a live parse) — there's no index to drift from there.
- **P2-6 Enforce `--scope` (hard-fail) for CLI `plan`/`recon`.** ✅ `requireScopeOrOptOut` (new, `cmd/hackerfive/scopeflag.go`) refuses to run without `--scope` unless `--allow-no-scope` is explicitly passed; `scan` deliberately keeps its existing warn-only behavior (its `--targets` is already the exact host list — no discovery-driven expansion happens there the way it does in `recon`'s own subfinder/katana waves). This is a considered reversal of doc15's own Definition of Done framing (which called CLI-warn/MCP-hard-fail an intentional, permanent split) — revisited because a `*.example.com`-style scope entry still authorizes the whole subdomain tree freely (`scope.Scope.Allowed`); the hard-fail only prevents running with literally no boundary, e.g. `some-cdn-vendor.net` turning up via a shared CNAME and getting silently touched. Set once per engagement (`.engagements/*/scope.txt`, gitignored — see the real `meesho`/`shopify` examples, or generate one from a live HackerOne program via `hackerfive report scopes --team <slug>`) and every subsequent run proceeds fully unattended, matching the user's explicit "run autonomously, warn/log rather than block" preference. The separate MCP `plan` tool's approve-before-execute elicitation gate (doc15 Step 2, doc90 Decision 5/6) was raised in the same discussion and explicitly kept as-is — not part of this item.

## Live Testing — nettix.com.pe (2026-09-04)

Real run against an owned target (`.engagements/owned-sites/scope.txt`; `docs/22-authorized-targets.md`'s new "Owned / operator-authorized targets" section): `hackerfive plan`/`hackerfive recon --recon-depth full` (22 real subdomains, 468-leaf plan tree, `pkg/registry/decisionengine.go`) plus a live Web UI Launch run (job `7151cee2a5fa681e`, misconfig/idor/authbypass/ssrf) via the already-running `hackerfive serve`. Full evidence in `/tmp/hf-nettix/{plan,recon}.json` on `~/projects/hacker-five`.

Numbered LT-1..LT-12, ordered by priority (1 = highest value-for-effort; tags are this session's estimate, not measured):

- **LT-1 [Impact: high | Effort: medium] Web UI Launch never dispatches the decision engine's own template-ranked leaves — the single biggest gap found.** `handlers_launch.go`'s `runLaunchRecon` (line ~526) calls `registry.Resolve` and gets a real 468-leaf tree back, but only uses it for one informational log line ("recon also suggests: X — not run"); it never runs any of the ~446 tag-ranked template leaves (real CVE/default-login/exposure checks) the engine already computed for this exact target. A Web UI user gets only the up-to-5 fixed native detectors they checked — the corpus-driven relevance ranking `plan`/`registry.Resolve` produces is invisible there unless they separately run CLI/MCP `plan`. Turning this into an actual opt-in "also run recon-suggested templates" dispatch (or wiring P2-1's `--llm-assist` in here too) would be the highest-value single change from this session.
- **LT-2 [Impact: high | Effort: low] `misconfig`'s `rejected()` (detector.go:377-379) still doesn't exclude 5xx — live false positive confirmed.** `PUT`/`DELETE`/`PATCH` against `https://nettix.com.pe/` all returned a plain nginx 502 (proxy failure, not an app response) and were reported as "appears to be accepted" at medium/high confidence. Same bug class as the already-fixed 404 case (Shopify note above) — 502/503/504 were never added to the exclusion list. One-line fix (extend the status-code exclusion set); directly protects the <5% FP target.
- **LT-3 [Impact: medium-high | Effort: low] `{Match: "swagger", ...}` (decisionengine.go:64) never fires from a real swagger.json.** `erp.nettix.com.pe/swagger.json` is live, 200 OK, and specifically recorded as an `APISpecFact` (`crawl.go`'s `specPaths`) — but `matchTechRules` only reads `ReconResult.TechStack`, never `.APISpec`, so the one rule meant for exactly this signal never triggers `idor`. Across the whole 468-leaf tree, native `idor`/`authbypass`/`ssrf` capability matches never fired anywhere — that path depends entirely on `resolveEndpointFacts`' endpoint-derived heuristics, and this target's shallow (`-depth 2`, no JS rendering) katana crawl never gave them an ID-shaped/param-shaped endpoint to key on. Fix is narrow: check `ReconResult.APISpec` alongside `TechStack` in `matchTechRules`/its caller.
- **LT-4 [Impact: high | Effort: medium-high] `hosterrors.Cache` silently dropped 13/22 hosts (59%) from Wave 3.** `pkg/scanner/hosterrors/cache.go`'s shared per-host circuit breaker (threshold 5) skips `probeCommonPaths`/`tagAuthBoundary` (`pkg/recon/crawl.go:203-229`) with zero warning once tripped — confirmed by diffing `recon.json`'s 22-host list against which hosts actually got `wave3-*`-sourced `EndpointFact`s. Includes `guacamole01.nettix.com.pe`, dropped even though `katana-crawl` reached it fine moments earlier in the same run (likely a `r.client` TLS-config mismatch vs. katana's own client, not investigated further here). Effort is medium-high because the root cause (why wave3's client fails where katana's doesn't) isn't confirmed yet — needs investigation before a real fix, not just a threshold/logging tweak.
- **LT-5 [Impact: medium | Effort: medium] SSE `/catchup` (`handlers_scan.go`) only re-syncs `#progress`/`#recon-results`, never `#logs`/`#findings`.** Confirmed live (zero log/finding entries in a `/catchup` fetch after several real log lines and 9 findings had already streamed). A client that connects late or reconnects mid-run permanently loses everything that arrived before that point.
- **LT-6 [Impact: medium | Effort: low-medium] Duplicate findings for one fact.** 4 native missing-security-header findings plus the nuclei `http-missing-security-headers` template both fired against the identical `https://nettix.com.pe` response, 30s apart — 5 findings for what's really one fact. Needs a dedup key (target+finding-class) at aggregation, not per-detector.
- **LT-7 [Impact: high | Effort: high] `matchTemplateTags` is still version-blind (P0-1b, already tracked above) — live-confirmed.** All 9 real Nginx hosts here got the identical top-8 CVE/traversal template list regardless of actual server version (which recon never captured for Nginx at all in this run); `scoreTemplateForTech` (`decisionengine.go:339-390`) only ever uses `version` as a stale-CVE penalty, never an affected-range gate. Bigger design change: needs an index schema carrying affected-version ranges (P1-4's own note) plus real version extraction for Nginx, not just a scoring tweak — kept lower in this ordering purely on effort, not on value.
- **LT-8 [Impact: medium | Effort: medium-high] `katana` crawl is hardcoded to `-depth 2`, no JS-rendering/headless mode, no CLI flag for either.** Positive baseline: a single `katana` subprocess already crawls all 22 discovered hosts together (`crawl.go:42-70`), not per-host — genuinely efficient. But the shallow, non-JS crawl plausibly explains why the endpoint-driven idor/ssrf heuristics found nothing on a real target with a live login boundary on 7 hosts. Effort is medium-high: headless mode has real perf/timeout tradeoffs across 22 hosts, not a flag flip alone.
- **LT-9 [Impact: low-medium | Effort: medium] `guacamole01` hostname signal unused.** The corpus already has `apache-guacamole`/`guacamole-default-login` templates; nothing in `pkg/registry`/`pkg/recon` tries a product-specific probe from a hostname that literally names the product. Needs a new hostname→product heuristic, not a one-line fix.
- **LT-10 [Impact: low | Effort: low] Google Analytics → 3 keyword-collision templates** (`piwik-unauthenticated-access`/`sonicwall-analytics-panel`/`versa-analytics-server` — zero real relevance, matched purely on the shared "analytics" tag word). Same denylist/tag-precision mechanism as P0-5/P0-2 — likely a quick addition to `nonActionableTech` or a tag-word exclusion.
- **LT-11 [Impact: low | Effort: low] `recon`/`plan` CLI commands emit zero stderr output even at `--recon-depth full`.** No progress/warning visibility outside the final JSON; the Web UI's own internal wave-by-wave progress logging (`waveDescription`, `job.AppendLog`) has no CLI equivalent at all. Low effort: route the same log strings to stderr behind a `--verbose` flag.
- **LT-12 [Impact: low | Effort: low] Web UI Launch's "misconfig" detector selection additively runs the full synced corpus too, not just CLI `scan --detector`** (confirmed: findings included a `nuclei-http-missing-security-headers-0` hit alongside native misconfig findings) — CLAUDE.md's documented gotcha applies here as well, just not called out for this path specifically. Documentation-only fix (or subsumed once LT-1 redesigns Web UI template dispatch).
