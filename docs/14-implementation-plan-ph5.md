# Phase 5 Implementation Plan — Weeks 33-40 (Recon & Orchestration Foundations)

> Part of the [HackerFive documentation set](../README.md).

**New phase carved out during the 2026-08-29 recon-phase restructuring.** The original Phase 5 draft ([15-implementation-plan-ph6.md](15-implementation-plan-ph6.md), then numbered "Phase 5") bundled the MCP server together with a set of foundations — the eval harness, the frozen `Finding` schema, and the `Job.PlanTree` data model — that don't actually need the MCP server to exist first. [91-research-recon-phase.md](91-research-recon-phase.md)'s research on recon added a third, larger foundation to that list (a whole new `pkg/recon/` package) and surfaced the concrete reason to split it out into its own phase rather than compress it into Phase 6's existing week count: **doc15 Step 1 already flags the MCP Go SDK's `elicitation`/`tasks` support as unverified — an external risk this project doesn't control.** Everything in this phase is buildable and testable via CLI alone, with zero dependency on that SDK working. If it turns out to be a rocky integration, recon and the task-tree data model still ship real, standalone value on schedule; nothing here is wasted.

## Objective

Doc90's proposed agent flow (plan → approve → scan → triage) has no step that produces the facts a coordinator would actually reason from, and no data model for the plan itself to live in — doc91 §1 makes the case directly: an LLM reasoning about a target it hasn't looked at yet reasons from priors, not facts. This phase builds the four foundations everything else in Phases 6-7 depends on:

1. **A recon phase** (`pkg/recon/`) that narrows the template search space, grounds the coordinator's first plan in observed facts instead of hallucination, and produces the signal doc90's B4 scope-creep gate has been missing a producer for.
2. **A frozen `Finding` schema** an external MCP client can depend on without the wire shape changing later.
3. **A `Job.PlanTree` data model** doc90's Group H names but never gave a concrete shape or a data source to seed from.
4. **A deterministic decision engine + capability registry** (`pkg/fingerprint`, `pkg/registry` — doc90 Decision 6/Group I, added 2026-08-30) that actually populates #3's `PlanTree` from #1's `ReconResult`, with zero LLM or agent involvement — the concrete answer to "how does a fingerprinted technology turn into a chosen detector/template" that doc91's original draft left implicitly assigned to "the coordinator" (i.e., an LLM). This is also what makes #3 real infrastructure rather than a data type nothing populates until Phase 6.

**Real architectural finding from cross-checking doc90 against the actual codebase, not transcribed blind:** doc90's Decision 4 and its Group H items (H2/H3) assumed `Finding.Confidence` doesn't exist yet and proposed adding it as "the field the agent does get to set." **It already exists** (`pkg/detectors/types.go`): `Finding.Confidence string` — `"high"` for cross-account baseline evidence, `"low"` for a single-account heuristic needing manual triage — and it's already detector-set, not agent-writable, exactly like `Severity`. Doc90's underlying goal (agent-writable confidence, distinct from deterministic severity) is still correct, but the field must not be `Finding.Confidence` — that name is taken and already carries a different, narrower meaning (evidence quality of the match, not the agent's success-probability estimate for a candidate it hasn't run yet). This plan's Step 2 puts the agent-set, Cyber-AutoAgent-banded confidence on the task-tree leaf (`PlanTree` node, not `Finding`) instead. This is, if anything, a stronger version of Decision 4 than doc90 drafted: *two* `Finding` fields (`Severity` and `Confidence`) are already deterministic and agent-proof, not one.

**A second finding, from doc91's research, worth restating here since it grounds this whole phase's design posture:** every comparable agentic pentesting tool researched (Strix, CAI, MAPTA, PentestAgent, and functionally Cyber-AutoAgent) gives its agent a general shell/terminal for reconnaissance specifically, not a narrow tool — even HexStrike, the one project with genuinely scoped per-binary MCP wrappers, ships a raw command-execution endpoint alongside them. HackerFive's `pkg/recon/` design below (fixed waves, a schema-scoped tool, no shell) is a deliberately conservative outlier relative to the field, trading some recon completeness for keeping Decision 2's "no shell tool, anywhere in the server" boundary genuinely absolute — see doc91 §5 for the full tradeoff, stated plainly rather than glossed over.

**Explicitly out of scope for this plan, named rather than silently dropped:**
- **A peer-agent mesh of any kind** — Decision 1 (doc90) is a permanent architectural boundary, not a v1 limitation to relax later.
- **Anything shell/exec-shaped, in the MCP tool surface or the recon tool** — Decision 2, same permanence; doc91 §5's design-tension callout explains why recon specifically doesn't get a carve-out despite the field's near-universal practice of giving recon a shell. (This governs what's exposed *to an agent*, not `pkg/recon`'s own internal use of fixed, named-binary subprocess calls per the Dependencies section above — the same distinction `pkg/templatesync`'s scoped `git` call already established.)
- **The MCP server itself, the `plan`/`elicitation` approval flow, and anything that requires an agent to actually be calling HackerFive** — that's Phase 6 ([15-implementation-plan-ph6.md](15-implementation-plan-ph6.md)); this phase produces the data (`ReconResult`, `PlanTree`) Phase 6 consumes, it doesn't consume it itself.
- **An actionable (approve/reject) version of the Plan-preview UI page** — this phase's Step 4 ships a *read-only* view of a `PlanTree`. **Updated 2026-08-30:** that tree is now real (Step 3's R8 decision engine populates it from a real `ReconResult`, no agent needed), but there's still no `elicitation` flow to approve/reject against — making the page actionable is still Phase 6 Step 4's job, just against real data sooner than originally planned.
- **A live Web UI Agent tab with SSE-streamed reasoning** — Phase 7 Step 3; nothing to stream yet.
- **ffuf (parameter/endpoint fuzzing) and gau/waybackurls (passive historical-URL discovery)** — the 2026-08-29 tool-stack survey flagged both as reasonable Go-native additions, but ffuf's request volume needs to be reconciled with the existing rate limiter before it's safe to schedule, and neither is load-bearing for Steps 1-5 above. Backlogged for a later Step within this phase if time allows, or Phase 7, rather than silently dropped.
- **Any LLM invocation of any kind, at any tier.** Decision 5/6 (doc90) is explicit that the deterministic decision engine (this phase) and the tiered LLM fallback (Phase 6) are separate, sequenced concerns. A `TechFact`/leaf the registry can't match stays a visibly unresolved `PlanTree` leaf — logged, inspectable, never silently escalated to a local or frontier model from this phase's code. That's Phase 6 Step 2's job (doc15).

## Dependencies used in this plan

**Revised from this doc's earlier draft, based on a 2026-08-29 tool-stack survey across eight comparable agentic pentesting products** (XBOW, Strix, CAI, MAPTA, HexStrike AI, Cyber-AutoAgent, PentestGPT, PentestAgent): `pkg/recon/` shells out to a fixed set of prebuilt ProjectDiscovery binaries — **subfinder** (Wave 1 subdomain/DNS enum), **tlsx** (Wave 1 cert inspection), **dnsx** (Wave 2 DNS resolution), **naabu** (Wave 2 port scan), **httpx** (Wave 2 HTTP probe/fingerprint), **katana** (Wave 3 crawl) — via `exec.CommandContext` with fixed, non-agent-controlled arguments, the same scoped-subprocess precedent `pkg/templatesync` already sets for `git` (`pkg/templatesync/sync.go`). This reverses the original "Go stdlib first, reimplement everything" stance for these six specifically: the survey found they're the dominant Go-native tools across the field (each used by 3-4 of the 8 products surveyed), and reimplementing their maturity from scratch in stdlib isn't a good use of Weeks 36-37 — whereas shelling out to fixed, named binaries with fixed flags is exactly as scoped as `templatesync`'s `git` call. This does not touch Decision 2: that decision governs what's exposed *to the agent* (Phase 6's MCP tool surface), not how `pkg/recon` implements itself internally. Each binary is a new runtime prerequisite (document in [04-environment-and-testing.md](04-environment-and-testing.md), same class of requirement as `golangci-lint`'s PATH note) — verify current stable versions/install instructions for each at implementation time per this project's own version-verification rule, don't assume whatever versions were current when this survey was run are still current. **How an end user without a Go toolchain actually gets these 6 binaries installed was left open here** ("document in doc04" meant the manual `go install` path, which still requires Go) — closed in `v0.5.1`'s `hackerfive recon setup` (`pkg/toolsync`): downloads, checksum-verifies, and installs each tool's real latest release directly, no Go toolchain needed, mirrored in the Web UI's `/recon` page. A standalone follow-up shipped just after this phase's `v0.5.0`, not folded into Phase 6/7's own week count, since it only touches `pkg/recon`/`pkg/webui`.

## Step 1: Foundations — Ratify Design Decisions + Eval Harness Stub (Week 33) — ✅ done (2026-08-30)

### Design

No code changes to `pkg/scanner`/`pkg/detectors` this week — this step is deliberately sequenced first per doc90's own sequencing note ("G1 first, even before A1/B1: without it, every claim this effort makes about agent quality is unfalsifiable from day one").

- **Ratified Decisions 1-6**, recorded here as committed project design for this phase, not re-litigated per step (full text: [90-research-hackerbot.md](90-research-hackerbot.md)): (1) single coordinator, no peer-agent mesh; (2) no shell/exec-shaped MCP tool anywhere, including for recon (per doc91's finding above); (3) MCP `elicitation`/`tasks` for approval; (4) the corrected Decision 4 — task-tree-leaf `Confidence`, not `Finding.Confidence` (see Objective above); (5) stateless, per-`PlanTree`-leaf, tiered LLM invocation — never a persistent agent session; (6) deterministic decision-engine dispatch first, LLM fallback only on a registry miss (see Step 3's R7-R9).
- **G1 — eval harness stub, built.** `tests/eval/` (build-tagged `eval`, opt-in like `tests/integration`, excluded from `go test ./...`/CI by default — run via `make eval`) runs the real `hackerfive scan` CLI (built once by `TestMain`, no agent involved) against each lab target already used throughout this project (crAPI, DVWA, Juice Shop, vAPI), reusing the *existing* `tests/fixtures/expected-findings/*.json` fixtures and mirroring `scripts/measure-fp-rate.sh`'s six scan invocations 1:1 (`tests/eval/challenges.go`'s `Scenarios`). Each fixture's `expected_id_prefixes` entry becomes one binary pass/fail challenge (`tests/eval/eval_test.go`); the same run's unexpected-finding count is logged alongside as an informational FP baseline, never a gate — this stub's job is narrow: prove the harness mechanism and produce today's detector-only baseline before an agent exists to drive it. Phase 7 Step 7 (G1 maturity) extends this into the actual agent-driven benchmark. One deliberate behavior difference from `measure-fp-rate.sh`: the DVWA scenario requires `DVWA_COOKIE` (skipped, not run, without it) rather than treating it as optional — running without it would otherwise report a false "FAIL" on the xss-/sqli- challenges that fixture's own description already documents as unreachable without a session cookie.

## Step 2: Finding Schema Freeze + Task-Tree Data Model (Weeks 34-35) — ✅ done (2026-08-30)

### Design

**A3 — freeze and version the `Finding` JSON schema.** Published `docs/schema/finding.schema.json` (JSON Schema 2020-12) reflecting the actual current struct (`ID`, `Type`, `Severity`, `Confidence`, `Target`, `Description`, `Evidence` — `pkg/detectors/types.go`), confirmed against every real `Finding{...}` literal in `pkg/detectors/**` and `pkg/template/nuclei/executor.go` (grepped, not assumed): `Severity` is a genuinely closed 4-value enum (`low`/`medium`/`high`/`critical`), `Confidence` a genuinely closed 2-value enum (`high`/`low`), both annotated in the schema's own `description` fields as detector-set and never agent-writable (the corrected Decision 4 from this doc's Objective). `Type` stays an open `string` (documented known values as examples, not an `enum`) since new detectors add new values over time. `additionalProperties: false` and all 6 fields `required`, matching the Go struct having no optional fields. This lands before Phase 6's MCP server, per doc90's own sequencing note.

**H2 — `Job.PlanTree`.** New shared type `pkg/agenttask` (importable by both the future `pkg/mcpserver` and `pkg/webui` without either depending on the other): a PTT-shaped tree (`PlanTree.Root *PlanNode`), each `PlanNode` a candidate `(Target, Detector)` pairing with `Status`, `Rationale`, and `Confidence`. **Mutations are restricted to leaves** via `PlanTree.ApplyLeafUpdate(nodeID string, patch PlanNodePatch) error`: `PlanNodePatch` carries only `Status`/`Confidence`/`Rationale` as mutable fields, plus a `Children []*PlanNode` field that exists *specifically* so a shape-changing request can be recognized and rejected (`ErrShapeChange`) rather than merely omitted from the API; a target node that itself has children is also rejected (`ErrNotLeaf`) — mirrors PentestGPT's own defense (doc90 §2) against a hallucinated rewrite of the overall plan. Tree construction (building the initial shape) uses the exported `PlanNode`/`Children` fields directly — no separate builder API, since nothing populates a real tree from a `ReconResult` until Step 3.

**Forward-note, not a Phase 5 defect:** `PlanTree`/`PlanNode` carry no mutex. Safe today — every Phase 5 caller (`registry.Resolve`, Step 3) builds a tree once, sequentially, and nothing in this phase calls `ApplyLeafUpdate` from more than one goroutine. Phase 6's planned PlanTree executor (doc15 §2 addendum, added 2026-08-31) will call `ApplyLeafUpdate` concurrently across parallel leaf executions — that step must add the mutex first, mirroring `pkg/webui`'s `Job`/`ReconJob`, which both already guard their mutable fields this way.

**H3 (corrected) — leaf-level `Confidence` bands, on `PlanTree` leaves, not on `Finding`.** `agenttask.Confidence` (`ConfidenceHigh`/`Medium`/`Low`) plus `BandConfidence(percent float64) Confidence`, banded per Cyber-AutoAgent's convention: High (>80%), Medium (50-80% inclusive), Low (<50%). This is the agent's own success-probability estimate for *attempting* a candidate — it never touches a `Finding` once one is actually produced; `Finding.Confidence`/`Finding.Severity` stay exactly as they are today, both deterministic.

**Dependency added: `github.com/santhosh-tekuri/jsonschema/v5`** (real JSON Schema validator, not a hand-rolled round-trip check) — its real transitive footprint was checked before committing to it, per this project's own dependency rule: a disposable scratch-module `go get` showed **zero transitive dependencies**, pure Go, one `go.mod` line. `go.sum` confirms the same in the real module.

### Files
- `docs/schema/finding.schema.json` — new, frozen/versioned schema.
- `pkg/agenttask/plantree.go` — `PlanTree`/`PlanNode`/`PlanNodeStatus`/`Confidence` types, `BandConfidence`, `ApplyLeafUpdate` mutation guard.
- `tests/unit/plantree_test.go` — `BandConfidence` boundary cases; `Find`; `ApplyLeafUpdate` allowed (leaf update) and rejected (shape-change patch, non-leaf target, unknown node ID) cases.
- `tests/unit/finding_schema_test.go` — compiles the schema once; round-trips real `Finding` values produced by actually running `idor`/`misconfig`/`authbypass`'s real `Run` methods against local `httptest` servers (reusing `detector_idor_test.go`'s existing `loadIDORFixture`/`newFixtureServer` helpers and `idor_classic.json` fixture, and `detector_misconfig_test.go`'s `withPrefix` helper — same package, no fixtures duplicated); a negative test (`TestFindingSchema_RejectsInvalidSeverity`) proves the validator actually rejects a bad enum value rather than passing vacuously.
- `go.mod`/`go.sum` — added `github.com/santhosh-tekuri/jsonschema/v5`.

All 12 new test cases pass on the first real run against actual detector output (not mocked schema data): 3 detector round-trips (idor/misconfig/authbypass) validate and round-trip losslessly, the invalid-severity negative case correctly fails validation, and all 5 `PlanTree` mutation-guard cases (1 allowed + 3 distinct rejection paths + `Find` hit/miss) pass. ## Step 3: Recon Package + Decision Engine (Weeks 36-37) — ✅ done (2026-08-31)

### R1/R1b/R2/R3 — what's actually built, live-verified

**R1 — `pkg/recon`.** Built as designed below, with three real corrections from live implementation (not glossed over):
- **Wave 2/3 field-name mapping was verified against each binary's actual JSON output, not assumed**: naabu identifies a result by `"ip"`, not `"host"`; httpx's tech list is `"tech"` and its resolved IP is `"host_ip"` — both confirmed by running the real installed binaries against real crAPI/DVWA output before writing the parser, not guessed from docs.
- **A real scope-bypass bug found and fixed during live testing**: an earlier version unconditionally re-added the target's own `host:port` to Wave 2's `httpx` input (to preserve a non-default port passive subfinder/tlsx enumeration can't discover), which bypassed the Wave 1 scope filter for the one host most likely to be scope-checked deliberately. Fixed by checking the target itself against `--scope` *before* Wave 0 ever fires (mirroring `pkg/scanner/engine.go`'s own `loadScope` convention: an explicitly-given target not covered by `--scope` is skipped entirely, not touched) — regression-tested by `TestRun_ExplicitTargetOutOfScope_SkipsEntirely` (`pkg/recon/recon_test.go`), which fails loudly (via an `httptest` handler that calls `t.Errorf` if ever hit) if this regresses.
- **katana's own default scope (`-fs rdn`, confirmed via its real `-h` output) already keeps it from fetching links outside a crawl seed's root domain** — an out-of-scope link it merely *noticed* (tagged with a non-empty `"error"` field, e.g. `"max depth reached"`, instead of a real response) is routed into `ReconResult.OutOfScope` if its host doesn't match a seed's, rather than silently dropped or miscounted as a confirmed `EndpointFact`.

Honest scope cuts (named per this doc's Context/discipline, not silently dropped): generic OpenAPI/GraphQL spec *parsing* is deferred — Wave 3 only detects a spec's presence as an `EndpointFact` via `probeCommonPaths`, `APISpec` stays `nil`. Hidden-parameter mining (Arjun-style) has no Go-native tool and isn't implemented. JS-bundle parsing relies entirely on katana's own `-jc` flag, no separate parser. Wave 4 doesn't tag facts against HackerFive's own template vocabulary — that's R8's job.

**R1b — `pkg/oob`, extracted from `pkg/detectors/ssrf/oob_client.go`.** Same real, RSA-OAEP+AES-256-CTR Interactsh-protocol client, now exported and shared (`Client`/`NewClient`/`NewClientWithFallback`/`Interaction`/`CorrelationIDLen`). `pkg/detectors/ssrf` updated to consume it; its own existing live test (`TestSSRFOOBCallback_RealEncryptedRoundTrip_Hit`) still passes unmodified. New `tests/unit/oob_test.go`'s `TestOOBClient_SelfIssuedCallback_RealServer` is a standalone, non-SSRF-detector live test against the real self-hosted `oob-server` container — skip-not-fail without `OOB_SERVER_URL` set, live-verified passing against `http://localhost:8082`.

**R2 — `docs/schema/recon-result.schema.json`**, same frozen/versioned discipline and `github.com/santhosh-tekuri/jsonschema/v5` validator as `finding.schema.json` (Step 2's A3) — no new dependency. `pkg/recon/schema_test.go` round-trips a real `ReconResult` (every wave exercised via an injected fake binary-runner plus a real local `httptest` server for Wave 0/3's own direct HTTP calls) through the schema.

**R3 — `hackerfive recon`** (`cmd/hackerfive/recon.go`): `-t/--targets`, `--recon-depth passive|active|full` (default `passive`), `--scope`, `--rate-limit`/`--concurrency` (also passed through to every external binary's own native rate/concurrency flag — see below), `--insecure`, `-o/--output` (shared root flag). Live-verified against real crAPI (`:8888`) and DVWA (`:80`) at every depth, including a real `--scope` file that correctly produces zero Wave 2/3 activity when the target itself is excluded.

**Rate-limit/concurrency, honestly reconciled**: binary-shelled waves are separate OS processes that structurally cannot route through `pkg/scanner/httpclient`'s Go middleware. Resolution: the same configured numbers (default 50 req/s / 25 concurrency, matching `scan`'s own defaults) are passed to each binary's own native flag (`naabu -rate`, `httpx -rl`/`-threads`, `katana -rl`/`-c`, `dnsx -rl`, `subfinder -rate-limit`) — verified against each tool's real `-h` output, not guessed. Wave 0/3's own direct HTTP calls (`security.txt`, `probeCommonPaths`, the auth-boundary heuristic fetch) go through the real `httpclient.Client` + `hosterrors.Cache`, identical to every existing detector.

### R7/R8/R9 — what's actually built, live-verified (2026-08-31)

**A real gap found during R8's implementation, not glossed over: `TechFact` had no `Host` field.** Step 3a's `ReconResult.TechStack` was a flat list with no record of which host produced each tech signal — harmless until R8's decision engine needed a `Target` for every `PlanTree` leaf it builds. Fixed in `docs/schema/recon-result.schema.json` (bumped to `$comment: "v1.1"`, `TechFact.host` now required) before Phase 6's MCP server — the only planned external consumer — exists to depend on the old shape.

**R7 — `pkg/fingerprint`.** A static signature table (`Signature{Product, HeaderName, HeaderContains, BodyContains, FaviconHash, Port}`, ~20 hand-authored entries) matching header/body/favicon/port signals, modeled on HexStrike's `TechnologyDetector` per this doc's own framing — authored fresh since no signature table is transcribed anywhere in this project's docs. Wired into `pkg/recon/active.go`'s `runHTTPX`: adding `-favicon -irr` to the existing httpx invocation (confirmed against the real binary's actual JSON output, not assumed) surfaces `header`/`body`/`favicon` per record, which `fingerprint.Detect` matches alongside the port list naabu already collected — enriching `TechStack` on top of httpx's own `-tech-detect` list, not replacing it. `Confidence` is banded by which signal fired: header/favicon match → high, body substring → medium, port-only → low. One signature (`crAPI`, favicon hash `-254193850`) is a real, live-confirmed value from the actual running lab container, not a guess.

**R8 — `pkg/registry`.** `Capabilities` (`pkg/registry/registry.go`) hand-transcribes doc01's [Capabilities at a Glance](01-overview-and-strategy.md#capabilities-at-a-glance) table (6 detectors, 7 recon tools, 4 template categories) into the `name`/`description`/`when_to_use`/`when_not_to_use`/`cost`/`risk`/`inputs_required` shape doc90's I1 specifies. `Resolve` (`pkg/registry/decisionengine.go`) groups a `ReconResult`'s `TechStack` by host, and for each `TechFact` emits: a `StatusPending` leaf per matched `techRules` entry (a small, hand-authored tech-name → capability-name table), a `StatusPending` leaf per matching template tag in R9's index (capped at 5 per tech), or — if neither matched — one `StatusUnresolved` leaf, visible and inspectable rather than dropped (Decision 6). Built via plain `*agenttask.PlanNode{...}` struct literals per `pkg/agenttask`'s own documented convention (no builder API exists).

**R9 — `templates/index.json`.** Almost entirely already-existing machinery: `pkg/templatesync.List` already flattens the bundled + synced template corpus into exactly R9's needed shape; this pass added JSON tags to `templatesync.Entry` (safe, additive) and a new `hackerfive templates index [-o templates/index.json]` subcommand. The generated file is gitignored (`/templates/index.json`) — a regenerable artifact, same posture as `.nuclei-templates-cache/`, not something to commit and have go stale.

**Wiring it end to end — `hackerfive plan`** (`cmd/hackerfive/plan.go`, not named in this doc's original R8 Files list but added for the same reason `hackerfive recon` was added for R3: this step's own Definition of Done needs a live-verifiable entry point). Runs `pkg/recon` inline, loads `templates/index.json` (a missing file degrades to skipping template-tag matching with a warning, not a hard failure — same posture as a missing recon binary), calls `registry.Resolve`, prints the resulting `PlanTree` as JSON.

**Docs:** README.md gained a short "Recon & Planning" section; `docs/04-environment-and-testing.md` now also notes the Dockerfile doesn't bundle the 6 recon binaries (`docker run hackerfive recon --recon-depth active` degrades to Wave 0-1 only, not a hard failure) — a real, deliberate gap named rather than left for someone to discover silently.

## Step 7: Recon-Derived Field Suggestions (Deterministic Pre-fill) — ✅ done (2026-09-01)

**Carved out 2026-09-01**, prompted by a competitive re-check against Strix and PentestGPT (both need only a target — plus, optionally, free-text credentials — to start; neither ever asks a user to name an endpoint template, a protected-path list, or a parameter name up front) and the observation that HackerFive's own decision engine (Step 3's R8) already computes almost everything needed to close that gap, but Step 6's Unified Launcher deliberately made its output informational-only. This step is the resolution: extend Decision 6's already-ratified "deterministic first" principle from *which detector to run* (the existing `PlanTree`/`registry.Resolve` use) to *what value to put in that detector's required field* — a related but distinct problem `registry.Resolve` was never scoped to solve.

### Design

**The real blocker isn't "write a heuristic," it's a sequencing problem Step 6 created on purpose.** `parseLaunchSubmission` (`pkg/webui/handlers_launch.go`) builds and calls `scanner.Config.Validate()` on every checked detector **synchronously, at HTTP-submission time** — before the background job, and therefore before recon, ever runs. A blank `idor` `Endpoint` or `authbypass` `ProtectedPaths` fails validation and re-renders the form immediately; recon never gets a chance to produce anything to fill the gap with. Step 6's own text names why this shape exists ("detector selection happens on the landing form before recon ever runs, so by the time recon finishes there's nothing left to gate") — reviving pre-fill without addressing this would just silently not work, not merely be a smaller version of the feature.

**Resolution:** a checked detector's recon-fillable field (`idor`'s `Endpoint`; `authbypass`'s `ProtectedPaths`/`LoginPaths`/`LogoutPaths`) left blank has its requiredness check deferred instead of failing immediately — the detector's `scanner.Config` is still built and carried into the job, just not yet fully `Validate()`-checked. `runLaunchJob`'s existing recon-then-detectors sequencing (Step 6) is the natural point to close the gap: once the recon phase finishes (or fails), each deferred config gets its blank field(s) filled from the real `ReconResult`, then `Validate()`-checked for real. A field that still comes up empty (no recon result, or recon produced nothing usable) means that one detector's phase is skipped with a clear, visible log line ("idor: skipped — no `--endpoint` given and recon found no candidate; fill in manually and re-run") — the job doesn't fail outright, matching Step 6's own "missing recon tools degrade gracefully, never blocking Scan" posture, and misconfig/other checked detectors still run normally. **This mirrors PlanTree's `StatusUnresolved` leaf exactly**: a gap the deterministic layer can't close stays visible and inspectable, never silently dropped and never silently escalated to an LLM.

**Correction to this section's own original draft, found at implementation time, 2026-09-01: there is no `run_recon` checkbox to gate this on.** The paragraph above originally read "when `run_recon` is checked..." — but the recon-opt-out-removal pass (Step 6, same day) had already deleted that checkbox; recon runs unconditionally on every submission now. This actually simplifies the design: the fill-then-validate step always applies, no checkbox branch needed, and there's no "immediate-validation, no regression" case to preserve for a `run_recon`-unchecked path that doesn't exist. A user-typed value still always wins over a recon-derived one — that rule doesn't depend on the checkbox either way.

**Mechanically, "defer the requiredness check" needed a real code change, not just a skipped `if`:** `Config.Validate()` (`pkg/scanner/config.go`) is one monolithic function checking everything (targets, concurrency, detector-specific requiredness, `AuthToken`, etc.) — deferring only the two specific fields meant factoring it into an internal `validate(opts ValidateOptions) error`, with `Validate()` calling it with a zero-value `ValidateOptions{}` (byte-for-byte unchanged behavior for the CLI and every existing test) and a new `ValidateWithOptions(opts ValidateOptions) error` for `parseLaunchSubmission` to call with `SkipEndpointRequired`/`SkipProtectedPathsRequired` set per the blank field. Every other check, including both `AuthToken` checks, stays unconditional — deferring a credential check would just silently not work later, per the credential-fields limit named above.

**User-typed input always wins.** Pre-fill only ever applies to a field left genuinely blank at submission time — it never overrides a value the operator actually typed, including a value that happens to look wrong.

**What's actually deterministic here — narrower than "parse recon results" sounds:**
- **`authbypass`: `suggestPathsFromRecon` (`pkg/webui/handlers_launch.go`) — written fresh, not revived.** A second correction found at implementation time: `git log --all -S suggestPathsFromRecon` across the entire repo history returns zero hits, ever, and reading the actual pre-deletion `handlers_guidedscan.go` (`git show 15d44fd^:pkg/webui/handlers_guidedscan.go`) confirms it never contained this function — Guided Scan's v1 (`f0ff375`) never had a path-suggestion heuristic at all. This step's original draft (the paragraph above claiming it "already existed and was deliberately deleted") was simply wrong. Written fresh from this section's own spec instead: a 401/403-`StatusCode` `EndpointFact` → protected path; a fact whose `Source == "wave3-auth-boundary-heuristic"` or whose path looks login-shaped (contains "login"/"signin") → login path; a logout/signout-shaped path → logout path. Each blank field (`ProtectedPaths`/`LoginPaths`/`LogoutPaths`) is filled independently — a typed `ProtectedPaths` doesn't block a blank `LoginPaths` from being filled from the same recon pass.
- **`idor`: `recon.SuggestIDOREndpointCandidates` (`pkg/recon/suggest.go`, exported — third correction: this step's Files list originally spelled it lowercase, `suggestIDOREndpointCandidates`, which can't compile across the `pkg/webui`→`pkg/recon` package boundary it needs to cross).** Walks `ReconResult.Endpoints[].URL` (`pkg/recon/types.go`'s real `EndpointFact` shape), parses each with `net/url`, and looks for a path segment or query value matching a purely-numeric (`^[0-9]+$`) or UUID-shaped pattern — built via a targeted `strings.Replace` on the raw URL string rather than `url.Values.Encode()`, which would percent-escape the `{{`/`}}` placeholder. Each match becomes one `{{id}}`-templated candidate (e.g. an observed `/workshop/api/mechanic/mechanic_report?report_id=482` → candidate `/workshop/api/mechanic/mechanic_report?report_id={{id}}`). **If recon surfaces exactly one distinct candidate template, auto-fill it** (same blank-field-only rule above); **if it surfaces more than one, that's a genuine ambiguity a heuristic must not silently resolve by picking one** — list every candidate in the job's log instead ("idor: N recon-derived candidates found, none auto-selected — pick one via `--endpoint` and re-run") and skip that detector's phase, same as the zero-candidate case.
- **`idor` template-preview probe, addressing a named-but-unfixed gap directly.** Step 6's own text already flags that a wrong `EndpointTemplate` "silently yields zero findings with no validation catching it" — true whether the template came from this step's heuristic or was typed by hand. `idor.Detector` (`pkg/detectors/idor/detector.go`) gained `WithTemplatePreview(bool)` and `WithLogCallback(func(level, msg string))` options (mirroring `pkg/scanner.Engine`'s own `WithLogCallback` signature): before `Run`'s baseline/heuristic dispatch, if enabled, `previewOnce` fires a single substituted-ID GET against the resolved template (reusing the exact `renderEndpoint`/`fetch` helpers the real loop uses) and logs its raw status/body-length — no `Finding` emitted, and a render/fetch error here just logs a warning rather than failing `Run`. Gated behind a new `scanner.Config.IDORPreview`/`--idor-preview` flag, default `false`, so an existing scripted/CLI-only invocation sees no behavior change; `pkg/webui`'s Launch page always sets it `true` for the idor tab, since a Web UI operator benefits from the honesty check unconditionally. Wired only at the flag-driven `--detector idor` construction site in `pkg/scanner/engine.go` (`runDetector`'s `"idor"` case), deliberately *not* folded into the shared `idorOptions()` helper — that helper's option set is also consumed by `native.Executor.runIDOR` for idor-tagged native templates, which shouldn't fire an extra preview probe/log line per template run.
- **`ssrf`: `recon.SuggestSSRFParamsFromRecon` (`pkg/recon/suggest.go`, same exported-naming correction as above).** Matches query-parameter *keys* observed across `ReconResult.Endpoints[].URL` against a small, hand-authored keyword table (`url`, `uri`, `link`, `redirect`, `return`, `next`, `callback`, `webhook`, `target`, `dest`, `continue`, `src`, `img`, `image`, `avatar`, `feed`, `host`, `domain`, `path`) — the same "small curated table" shape already used elsewhere in this codebase (`pkg/registry`'s `techRules`, `pkg/detectors/misconfig`'s `MissingHeaders`/`VerboseErrorPatterns`), not a novel mechanism. **Scope note, named rather than silently assumed:** `ssrf` isn't one of the Unified Launcher's three current tabs (misconfig/idor/authbypass only, per Step 6) — this step builds and unit-tests the suggestion function standalone (reusable by `cmd/hackerfive/plan.go` or a future MCP tool, same "detector-UI-agnostic, lives in `pkg/recon` not `pkg/webui`" placement as the idor function above); actually adding an `ssrf` tab to the Web UI is a separate, not-yet-decided scope call, not bundled into this step.

**Credential fields — a different, unsolved problem, named here rather than silently out of scope, 2026-09-01.** `AuthToken`/`OtherAuthToken`/`ExtraHeaders` (`pkg/scanner/config.go`) are required inputs for `idor`/`authbypass`/`businesslogic`, and unlike the endpoint/path fields above, no amount of recon closes this gap — a session cookie or bearer token is a secret a target's own login flow issues, not an observable fact `pkg/recon` could ever fingerprint. This step doesn't attempt to auto-fill them, and shouldn't be read as having overlooked them. What's already true and worth stating plainly: all three fields sit inside the Launch page's closed-by-default Advanced Settings `<details>` (`launch.html`, Step 6's collapse), alongside the endpoint/path fields this step fills — a first-time or misconfig-only operator never sees a token prompt unless they open Advanced Settings themselves. Building actual login automation (drive the target's real login form from a supplied username/password, extract the resulting session cookie the same deterministic way this step derives endpoints) was considered and explicitly deferred as a separate, materially larger scope — real new work (login-form discovery, CSRF handling, multi-step logins), not a variant of this step's heuristic-fill mechanism — and is not decided against, just not this step's job.

**On the user's LLM-placeholder question — deliberately not built here.** It would make sense as a *concept* (the zero-/multiple-candidate cases above are exactly the shape doc90 Decision 6 already anticipates an LLM fallback for — "fires only on a deterministic miss," never a standing parallel path), but this phase's own Objective and "Explicitly out of scope" list both state "zero LLM invocation of any kind, at any tier" as a hard, repeated boundary — not an oversight this step gets to quietly relax. A code-level placeholder (a stub function, a disabled call site) would either be dead/untested code, or a quiet integration point someone wires up later without Phase 6 Step 2's own safety machinery around it (`pkg/llmfallback`'s spend ceiling, approval gate, and template-rejection pipeline, per [15-implementation-plan-ph6.md](15-implementation-plan-ph6.md) Step 2) — the exact failure mode Decision 6 exists to prevent. The correct move is the one already used for `PlanTree`'s unresolved leaves: render the gap honestly now, close it later. **Done, not just recommended:** [15-implementation-plan-ph6.md](15-implementation-plan-ph6.md)'s Objective and Step 2 (I4) are updated (2026-09-01) to make `pkg/llmfallback` explicitly serve two callers — an unresolved `PlanTree` leaf (detector selection) and an unresolved field suggestion from this step (`idor`/`authbypass`) — through the same stateless client with two small, distinct output schemas (`{use_existing_tag}`/`{draft_template}`/`{escalate_to_human}` for a leaf; `{suggested_value, rationale}`/`{escalate_to_human}` for a field, never a `draft_template` shape for the latter). Both still require `elicitation` approval before anything runs — a field suggestion doesn't get a lighter gate just because it's "only a string."
